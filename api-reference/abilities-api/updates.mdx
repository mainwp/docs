MainWP Dashboard 6.3 registers 14 update management abilities into the WordPress Abilities API framework. These enable programmatic control over WordPress core, plugin, theme, and translation updates across your network.

## What You'll Learn

- Listing available updates across all sites
- Applying WordPress core, plugin, theme, and translation updates
- Managing ignored updates
- Batch update operations
- Safe Updates runs with site checks and rollback

---

## Confirmation and Update Holds in 6.3

`run-updates-v1`, `update-all-v1`, and the four `update-site-*` abilities require either `dry_run: true` to preview or `confirm: true` to execute. A call with neither returns `mainwp_confirmation_required` with HTTP 400. Do not set both flags to true.

Preview first, review the returned sites and update plan, then submit the same selection with `confirm: true`. A direct Abilities API request uses these flags; the separate one-time confirmation token used by MainWP MCP belongs to the MCP server's [confirmation flow](/mcp-server/safety).

Previews return `dry_run`, `would_affect`, `count`, `warnings`, and `errors`. Confirmed immediate responses include `dry_run: false`, `skipped`, and `summary.total_skipped`. Inspect both `errors` and `skipped`; a successful HTTP request does not mean every update was installed. Queued responses return `job_id` and `status_url` for [status polling](/api-reference/abilities-api/batch-operations). Send an authenticated GET to `status_url` using your WordPress Application Password. The URL includes `input[job_id]` for `mainwp/get-batch-job-status-v1`.

These abilities respect site-level and global update holds. Pending items blocked by a hold appear as skipped, and queued jobs recheck holds, site access, and the job owner's operation permissions when they execute.

When **Ignore translation updates** is on for a site, `mainwp/list-updates-v1` and `mainwp/get-site-updates-v1` leave its translation updates out of their lists and counts. Update previews and execution results show them in `skipped` with `reason: ignored_site_flag`. Confirmed calls and queued jobs do not apply them, even when `slugs` or `specific_items` names a held translation. Turn the setting off to include the site's translation updates again.

Adding an update hold remains available through the ignore abilities. Removing a site's own holds uses the new `mainwp/unignore-site-updates-v1` ability with preview or confirmation. The older `action: unignore` and `action: remove` paths return an error directing you to that ability.

## mainwp/list-updates-v1

List available updates across all sites.

**Method:** GET (readonly)

```bash
curl -u 'admin:xxxx' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/list-updates-v1/run'
```

**Input Parameters:**

| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| `site_ids_or_domains` | array | No | [] | Filter to specific sites |
| `types` | array | No | [] | Filter: `core`, `plugins`, `themes`, `translations` |
| `page` | integer | No | 1 | Page number |
| `per_page` | integer | No | 50 | Items per page (max 200) |

**Response:**

```json
{
  "updates": [
    {
      "site_id": 1,
      "site_url": "https://site1.example.com",
      "site_name": "Site 1",
      "type": "plugin",
      "slug": "akismet/akismet.php",
      "name": "Akismet Anti-spam",
      "current_version": "5.3",
      "new_version": "5.3.1"
    }
  ],
  "summary": {
    "core": 2,
    "plugins": 15,
    "themes": 3,
    "translations": 5,
    "total": 25
  },
  "page": 1,
  "per_page": 50,
  "total": 25
}
```

## mainwp/run-updates-v1

Execute updates on sites. Operations affecting more than 200 sites are queued for background processing.

**Method:** POST

```bash
# Preview a specific plugin update on selected sites
curl -X POST -u 'admin:xxxx' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_ids_or_domains":[1,2,3],"types":["plugins"],"specific_items":["akismet/akismet.php"],"dry_run":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/run-updates-v1/run'

# Apply the same selection after reviewing the preview
curl -X POST -u 'admin:xxxx' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_ids_or_domains":[1,2,3],"types":["plugins"],"specific_items":["akismet/akismet.php"],"confirm":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/run-updates-v1/run'
```

**Input Parameters:**

| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| `site_ids_or_domains` | array | No | [] | Sites to update. Empty = all with updates |
| `types` | array | No | [] | Update types: `core`, `plugins`, `themes`, `translations` |
| `specific_items` | array | No | [] | Specific slugs to update |
| `dry_run` | boolean | For preview | false | Set true to preview; do not combine with confirm |
| `confirm` | boolean | For execution | false | Set true to execute after reviewing a preview |

Run a preview first with `dry_run: true`. The commands above show confirmed execution unless labeled as a preview.

**Response:**

```json
{
  "dry_run": false,
  "updated": [
    {
      "site_id": 1,
      "site_url": "https://site1.example.com",
      "site_name": "Site 1",
      "type": "plugin",
      "slug": "akismet/akismet.php",
      "name": "Akismet",
      "old_version": "5.3",
      "new_version": "5.3.1"
    }
  ],
  "errors": [],
  "summary": {
    "total_updated": 1,
    "total_errors": 0,
    "sites_updated": 1,
    "total_skipped": 0
  },
  "skipped": []
}
```

## mainwp/unignore-site-updates-v1

Preview or remove one site's own update holds. Removing a hold can make an update eligible for later update runs, including queued runs; this ability does not install the update.

**Method:** POST

```bash
# Preview removal of one plugin's site hold
curl -X POST -u 'admin:xxxx' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_id_or_domain":1,"type":"plugin","slugs":["akismet/akismet.php"],"dry_run":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/unignore-site-updates-v1/run'

# Remove that hold after reviewing the preview
curl -X POST -u 'admin:xxxx' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_id_or_domain":1,"type":"plugin","slugs":["akismet/akismet.php"],"confirm":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/unignore-site-updates-v1/run'
```

| Name | Type | Required | Description |
|------|------|----------|-------------|
| `site_id_or_domain` | integer or string | Yes | Authorized site ID or domain |
| `type` | string | Yes | `core`, `plugin`, or `theme` |
| `slugs` | array of strings | For plugin and theme | Nonempty list of item slugs; ignored for core |
| `dry_run` | boolean | For preview | Set to `true` to inspect the holds without changing them |
| `confirm` | boolean | For execution | Set to `true` to remove the site's own holds |

A preview returns `would_affect.holds`, a count, warnings, and errors. A hold's `still_held_by` field identifies a global or whole-site hold that will remain in effect. Execution returns `removed`, `not_held`, and `count` with `dry_run: false`:

```json

  "dry_run": false,
  "removed": [
    "akismet/akismet.php"
  ],
  "not_held": [],
  "count": 1
}
```

Global holds and whole-site ignore flags remain unchanged. Site access and **Ignore/Unignore Updates** permissions apply.

## Safe Updates Abilities

MainWP Dashboard X adds eight abilities in the `mainwp-updates` category for [Safe Updates](/sites/updates/does-mainwp-have-safe-updates): runs that check each site before and after updating, back it up first when your settings require it, and can roll back plugin and theme updates. The descriptions of `run-updates-v1` and `update-all-v1` point to `run-safe-update-v1` when you want those checks. Their inputs and results are unchanged.

| Ability | Inputs beyond `dry_run` and `confirm` | Result |
|---------|---------------------------------------|--------|
| `mainwp/run-safe-update-v1` | `site_ids_or_domains`, `types`, `specific_items`, `checks`, `ignore_backup_gate` | Preview, or `run_id`, `url`, and `conflicts` |
| `mainwp/list-safe-update-runs-v1` | `page`, `per_page` (1-100, default 25), `source` (`manual`, `auto`, or empty for both) | `items`, `total`, and pagination. Each run has `stalled`. |
| `mainwp/get-safe-update-run-v1` | `run_id` | `run`, the `rows` you can access, `stalled`, and `needs_tick` |
| `mainwp/continue-safe-update-run-v1` | `run_id` | Preview, or the result after one step |
| `mainwp/cancel-safe-update-run-v1` | `run_id` | Preview, or the result after requesting cancellation |
| `mainwp/retest-safe-update-site-v1` | `row_id` | Preview, or the result after the checks run again |
| `mainwp/resolve-safe-update-site-v1` | `row_id`, `revision` | Preview, or the result after marking the result as expected |
| `mainwp/rollback-safe-update-v1` | `row_id`, `revision`, optional `item_index` or `find_cause` | Preview, or the result after the rollback starts |

`list-safe-update-runs-v1` and `get-safe-update-run-v1` are read-only and do not move runs forward. Every other Safe Updates ability needs `dry_run: true` to preview or `confirm: true` to act. Sending both is refused. A preview returns `dry_run: true` and `would_affect`. A confirmed start returns `dry_run: false` with `run_id`, `url`, and `conflicts` at the top level. Confirmed actions on an existing run or row return `dry_run: false` and `result`.

A Safe Updates run is not a batch job. Poll `get-safe-update-run-v1`, not `get-batch-job-status-v1`. When a run shows `stalled: true` or `needs_tick: true`, calling `continue-safe-update-run-v1` runs the Safe Updates worker, which moves due work forward. WP-Cron, server cron, and an open run page also move runs.

### Start a Run

Selection inputs work as in `run-updates-v1`. An empty `site_ids_or_domains` selects every live site you can access; name a staging site to include it.

| Name | Type | Default | Description |
|------|------|---------|-------------|
| `checks` | string | `all` | One of `all`, `none`, `http`, `monitor`, `child`, `http,monitor`, `http,child`, `monitor,child`, or `http,monitor,child`. `http` loads the site, `monitor` reads its uptime monitors, and `child` asks MainWP Child. `none` turns off these three; the Regression test check still runs when available. |
| `ignore_backup_gate` | boolean | false | Same as **Update sites that have no recent backup without waiting for one** in the Safe Update preview |

```bash
# Preview a Safe Update of one plugin on one site with the HTTP check only
curl -X POST -u 'admin:xxxx' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_ids_or_domains":[5],"types":["plugins"],"specific_items":["sample/plugin.php"],"checks":"http","dry_run":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/run-safe-update-v1/run'
```

The preview's `would_affect.sites` lists each site's items, backup status, available checks, and skip reasons. Send the same selection with `confirm: true` to start the run. The response has the `run_id`, the run page `url`, and `conflicts`: the IDs of sites left out because another run holds them. Suspended sites appear in the preview and are left out when the run starts.

### Act on a Site Row

Row actions take `row_id` (`rows[].id` from `get-safe-update-run-v1`). Mark as expected and rollback also need the row's current `revision` (`rows[].revision`); the call is refused if the row changed since you read it. Read the run again after each action to get the new revision and the actions now available.

For `rollback-safe-update-v1`:

- Pass `item_index` (`rows[].items[].index` of an item with `can_rollback: true`) to roll back one item.
- Omit `item_index` to roll back every updated plugin and theme on the row. The request is refused if any of them has no usable kept copy or you lack the right to update it.
- After a full rollback fixed the checks, pass `find_cause: true` without `item_index` to re-apply the updates one at a time and keep only the failing ones rolled back.

Rollback does not undo database changes. Restore a backup instead when you need that.

### Permissions

These abilities use the same checks as the Safe Updates pages, including a WordPress administrator account on the Dashboard. Starting a run and rolling back need the update right for each item type. When the backup requirement applies to a selected site, starting a run also needs **Execute Backups**, unless `ignore_backup_gate` is true. The other abilities need any update right. All of them are limited to the sites you can access. You can cancel a manual run only if you started it or manage every site in it. Automatic update runs cannot be cancelled.
