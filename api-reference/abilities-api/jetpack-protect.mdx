<Note>
These abilities require a Jetpack Protect Integration release that includes Abilities API support. Earlier builds do not register them, and the eight site abilities appear only in releases that include them. Check ability discovery on your Dashboard before using these examples.
</Note>

The Abilities-enabled Jetpack Protect Integration registers up to ten abilities in the `mainwp-jetpack-protect` category. All of them use the `mainwp/` namespace on your MainWP Dashboard.

- Two **stored summary** abilities read data the add-on saved during earlier syncs. They do not start scans, sync sites, change settings, or contact child sites.
- Eight **site** abilities work on one site at a time. Five of them read saved or live state. Three of them ask the Dashboard to change a setting on the child site or fetch fresh results; that work runs in the background.

## What You'll Learn

- List stored Jetpack Protect connection flags and vulnerability counts for your sites
- Read the latest stored scan and its vulnerability summaries for one site
- Read a site's saved results, findings, and result history
- Check a site's live Jetpack connection and Protect visibility, then preview and request a change
- Request fresh Jetpack Protect results and follow background work until it finishes
- Understand what the responses leave out and why

## Prerequisites

- WordPress 6.9 or later on the MainWP Dashboard site
- MainWP Dashboard with Abilities API support; use version 6.2 or later for the `input_json` and DELETE request examples below
- The Abilities-enabled Jetpack Protect Integration, active on MainWP Dashboard
- An authenticated WordPress user with `manage_options` and access to the Jetpack Protect add-on
- Dashboard access to the target site for site-specific calls
- MainWP Child 6.4 or later on each child site you use with the site abilities that contact the child site or change it
- Working scheduled tasks (WP-Cron or a system cron job) on the Dashboard site for refreshes and changes

Use an [Application Password](/api-reference/rest-api/application-passwords) or the [authentication methods in the Abilities API overview](/api-reference/abilities-api/overview#authentication). The examples use an Application Password.

Set `MAINWP_USERNAME` and `MAINWP_APPLICATION_PASSWORD` in your shell to your WordPress username and Application Password. Keep their values out of shared scripts and logs.

The two stored summary abilities are limited to administrators. Users without `manage_options` are refused even when Team Control would otherwise grant access to the add-on. The eight site abilities use the Dashboard's standard Abilities permission check, then check access to the add-on and to the selected site.

## Available Abilities

| Ability | Method | Purpose |
|---------|--------|---------|
| `mainwp/list-jetpack-protect-sites-v1` | GET | List stored connection flags, last scan time, and vulnerability counts for accessible sites |
| `mainwp/get-jetpack-protect-site-scan-v1` | GET | Read one site's latest stored scan with up to 100 vulnerability summaries |
| `mainwp/get-site-jetpack-protect-observation-v1` | GET | Read one site's saved results summary |
| `mainwp/list-site-jetpack-protect-findings-v1` | GET | List one site's current findings, up to 100 per page |
| `mainwp/list-site-jetpack-protect-history-v1` | GET | List the total finding count from earlier saved results |
| `mainwp/get-site-jetpack-protect-control-state-v1` | GET | Ask the child site for its current Jetpack connection and Protect visibility |
| `mainwp/replace-site-jetpack-protect-connection-v1` | DELETE | Preview or request connecting or disconnecting Jetpack |
| `mainwp/replace-site-jetpack-protect-visibility-v1` | DELETE | Preview or request showing or hiding the Jetpack Protect plugin |
| `mainwp/request-site-jetpack-protect-refresh-v1` | POST | Request fresh Jetpack Protect results from the child site |
| `mainwp/get-site-jetpack-protect-operation-v1` | GET | Check the status of a refresh, connection, or visibility request |

Discover the abilities and their schemas:

```bash
curl -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities?category=mainwp-jetpack-protect'
```

All read abilities are annotated `readonly: true`, `destructive: false`, and `idempotent: true`. The connection and visibility abilities are annotated `readonly: false`, `destructive: true`, and `idempotent: true`, so WordPress requires **DELETE** for them, including previews. They change settings on the child site; they do not delete anything. The refresh ability is annotated `readonly: false`, `destructive: false`, and `idempotent: true`, so it uses **POST**.

## Request Rules

- `site_id` is a positive MainWP site ID such as `1`. Find IDs with the [Sites abilities](/api-reference/abilities-api/sites). The two stored summary abilities use it.
- `site_id_or_domain` is a MainWP site ID such as `1`, or the domain of a site already connected to your Dashboard. The eight site abilities use it.
- Inputs reject extra properties.
- Times are ISO 8601 UTC strings, such as `2026-10-28T23:46:53Z`. A time is `null` when no time is stored.
- Results include the same six `counts` fields: `total`, `core`, `plugins`, `themes`, `files`, and `database`.
- GET requests send input in the `input_json` query parameter. DELETE requests send `{"input":{...}}` as a JSON body, and so do POST requests.

## List Jetpack Protect Sites

**Ability:** `mainwp/list-jetpack-protect-sites-v1`<br />
**Method:** GET<br />
**Input:** `site_id`, `page`, and `per_page` (all optional)

| Input | Type | Default | Description |
|-------|------|---------|-------------|
| `site_id` | integer | None | Return only this site |
| `page` | integer | `1` | Page number, starting at 1 |
| `per_page` | integer | `20` | Sites per page, from 1 to 100 |

List all accessible sites:

```bash
curl -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/list-jetpack-protect-sites-v1/run'
```

Request a specific page:

```bash
curl -G -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  --data-urlencode 'input_json={"page":2,"per_page":50}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/list-jetpack-protect-sites-v1/run'
```

**Example response:**

```json
{
  "sites": [
    {
      "site_id": 1,
      "site_name": "Client Store",
      "connected": true,
      "scan_active": false,
      "plugin_hidden": false,
      "last_scan_at": "2026-10-28T23:46:53Z",
      "counts": {
        "total": 3,
        "core": 0,
        "plugins": 2,
        "themes": 1,
        "files": 0,
        "database": 0
      }
    }
  ],
  "page": 1,
  "per_page": 20,
  "total": 1
}
```

| Site field | Meaning |
|------------|---------|
| `site_id` | MainWP site ID |
| `site_name` | Site name from MainWP Dashboard |
| `connected` | `true` when the site's stored Jetpack connection flag is set |
| `scan_active` | `true` when the site's stored scan-active flag is set |
| `plugin_hidden` | `true` when the Jetpack Protect plugin is hidden on the child site |
| `last_scan_at` | Time of the last stored scan, or `null` |
| `counts` | Stored vulnerability counts by type |

The list includes only sites you can access that have stored Jetpack Protect data. `total` is the number of those sites. Increase `page` until you have read `total` sites. A page beyond the last result returns an empty `sites` array.


**Example response:**

```json
{
  "scanned_at": "2026-10-28T23:46:53Z",
  "counts": {
    "total": 2,
    "core": 0,
    "plugins": 1,
    "themes": 0,
    "files": 1,
    "database": 0
  },
  "vulnerabilities": [
    {
      "type": "plugin",
      "affected_item": "Example Forms",
      "installed_version": "2.1.0",
      "fixed_in": "2.1.4",
      "title": "Example Forms <= 2.1.3 - Cross-Site Scripting",
      "severity": "medium"
    },
    {
      "type": "file",
      "affected_item": "suspicious.php",
      "installed_version": "",
      "fixed_in": "",
      "title": "Malicious code found in file",
      "severity": "critical"
    }
  ],
  "truncated": false
}
```

| Vulnerability field | Meaning |
|---------------------|---------|
| `type` | `core`, `plugin`, `theme`, `file`, or `database` |
| `affected_item` | Name of the affected component. For file threats, only the file name is returned, not its path. |
| `installed_version` | Installed version of the affected component, or an empty string |
| `fixed_in` | Version that fixes the issue, or an empty string when unknown |
| `title` | Threat title reported by Jetpack Protect |
| `severity` | Severity reported by Jetpack Protect |

The response includes at most 100 vulnerability summaries. When more findings are stored, `truncated` is `true`. `counts` still reports the full stored totals, so use the [Jetpack Protect page](/add-ons/security/jetpack-protect-extension) to review the complete list.

If the site has no stored scan, the response returns `scanned_at: null`, zero counts, an empty `vulnerabilities` array, and `truncated: false`.

## How the Site Abilities Work

The eight site abilities share the rules below.

### Saved Results and Live State

The results summary, findings, and history abilities read results the Dashboard already saved. They never contact the child site. The Dashboard saves new results when you request a refresh, and when a site sync brings back results from MainWP Child 6.4 or later. A saved result counts as fresh for 24 hours. Earlier results are removed after about 90 days, but the latest result for each site is always kept.

The control state ability is different: it asks the child site right away for its current Jetpack connection and Protect visibility.

### Preview First, Then Confirm

The connection and visibility abilities need two flags, `dry_run` and `confirm`:

| Step | `dry_run` | `confirm` |
|------|-----------|-----------|
| Preview: see what would change, with no effect on the site | `true` | `false` |
| Request the change after reviewing the preview | `false` | `true` |

Sending both as `true` is rejected. Sending both as `false` returns `confirmation_required`.

### `if_match`: Send the Revision You Read

Before a change, read the control state. Its `revision` is a 64-character value that identifies the state you saw. Send it as `if_match` in both the preview and the confirmed request. If the site changed since you read it, the request returns `stale_revision`. Read the control state again and decide whether you still want the change. The child site checks the revision again when the change runs, so a change made in the meantime makes the request fail instead of overwriting it.

### `request_ref`: Retry Without Doing the Work Twice

`request_ref` is a UUID your client creates for each new request, such as `11111111-1111-4111-8111-111111111111`. Use a new version 4 UUID for each request, and keep it until you know how the request ended.

If a confirmed request times out or you are unsure it arrived, send the exact same input again with the same `request_ref`. The Dashboard recognizes it and returns the original response instead of starting a second change or refresh. Reusing a `request_ref` with different input returns `request_conflict`. Previews are not recorded, so `request_ref` has no effect on them.

### Requests Finish Later

A confirmed change or a refresh request returns right away with `status: "queued"` and an `operation_ref`. The work then runs in the background. Read its progress with [Get Operation Status](#get-operation-status) until the status is `succeeded`, `failed`, `unknown`, or `expired`.

A replayed request returns the original response, which can still say `queued` after the work has finished. Always use the operation ability for the current status.

Only one refresh, one connection change, and one visibility change can be in progress for a site at a time. Another request of the same type for that site returns `lock_busy` until the first one finishes.

### An `unknown` Result Is Final

`unknown` means the Dashboard sent the change but could not confirm what happened on the child site. The change may or may not have been applied. The Dashboard never retries or rechecks an `unknown` operation, and it stays `unknown`.

When you see `unknown`, read the control state to find out what the site looks like now. If you still need a change, submit a new request with a new `request_ref` and the new `revision` as `if_match`.

`failed` and `expired` operations are safe to retry with a new request; `retryable` is `true` for them. `expired` means the request waited more than an hour without starting, so nothing was sent to the child site.

### Background Work Needs Scheduled Tasks

Queued refreshes and changes run through WordPress scheduled tasks (WP-Cron) on the Dashboard site. If WP-Cron is disabled on the Dashboard and no system cron job runs `wp-cron.php`, queued work never starts. It stays `queued`, and new requests of the same type for that site return `lock_busy`. Once scheduled tasks run again, work that waited more than an hour becomes `expired`.

### MainWP Child Version

Reading the control state, changing the connection or visibility, and refreshing results need MainWP Child 6.4 or later on the child site. With an older version, the control state, previews, and confirmed changes return `unsupported_version` right away. A refresh is still accepted, but its operation ends as `failed`. Update MainWP Child on that site, then try again.

## Get Site Results Summary

**Ability:** `mainwp/get-site-jetpack-protect-observation-v1`<br />
**Method:** GET<br />
**Input:** `site_id_or_domain` (required)

Reads the saved results summary for one site. It does not contact the child site.

```bash
curl -G -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  --data-urlencode 'input_json={"site_id_or_domain":1}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/get-site-jetpack-protect-observation-v1/run'
```

**Example response:**

```json
{
  "site_id": 1,
  "availability": "available",
  "observed_at": "2026-10-30T08:15:00Z",
  "fresh_until": "2026-10-31T08:15:00Z",
  "connected": true,
  "scan_product_active": false,
  "counts": {
    "total": 2,
    "core": 0,
    "plugins": 2,
    "themes": 0,
    "files": 0,
    "database": 0
  },
  "revision": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

| Field | Meaning |
|-------|---------|
| `availability` | See the table below |
| `observed_at` | When the child site produced these results |
| `fresh_until` | When the results stop counting as fresh, 24 hours after `observed_at` |
| `connected` | Whether Jetpack was connected when the results were taken |
| `scan_product_active` | Whether the paid Jetpack Scan product was active |
| `counts` | Finding counts by type, or `null` when results are partial or missing |
| `revision` | Identifies this saved result |

| Availability | Meaning |
|--------------|---------|
| `available` | Complete, fresh results are saved |
| `stale` | Complete results are saved but are more than 24 hours old. Request a refresh. |
| `partial` | The child site sent incomplete results. `counts` is `null`. |
| `no_snapshot` | The site is connected, but no results in this format are saved yet. Request a refresh. |
| `not_configured` | No Jetpack Protect data is saved for this site |
| `malformed` | Saved results could not be validated and are not returned |

When `availability` is `no_snapshot`, `not_configured`, or `malformed`, all other fields except `site_id` are `null`.

## List Site Findings

**Ability:** `mainwp/list-site-jetpack-protect-findings-v1`<br />
**Method:** GET<br />
**Input:** `site_id_or_domain` (required), `kind`, `after_finding_ref`, and `limit`

Lists the findings in the site's latest saved results. It does not contact the child site.

| Input | Type | Default | Description |
|-------|------|---------|-------------|
| `site_id_or_domain` | integer or string | None | Site ID or domain |
| `kind` | string or `null` | `null` | Show only `core`, `plugin`, `theme`, `file`, or `database` findings |
| `after_finding_ref` | string or `null` | `null` | Start after this finding. Use `next_after_finding_ref` from the previous page. |
| `limit` | integer | `50` | Findings per page, from 1 to 100 |

```bash
curl -G -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  --data-urlencode 'input_json={"site_id_or_domain":1,"kind":"plugin","limit":50}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/list-site-jetpack-protect-findings-v1/run'
```

**Example response:**

```json
{
  "site_id": 1,
  "observed_at": "2026-10-30T08:15:00Z",
  "findings": [
    {
      "finding_ref": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
      "kind": "plugin",
      "title": "Example Forms <= 2.1.3 - Cross-Site Scripting",
      "component_name": "Example Forms",
      "remediation": "component_update_available"
    }
  ],
  "next_after_finding_ref": null,
  "truncated": false,
  "revision": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

| Finding field | Meaning |
|---------------|---------|
| `finding_ref` | Identifies the finding within this set of results |
| `kind` | `core`, `plugin`, `theme`, `file`, or `database` |
| `title` | Finding title, up to 160 characters |
| `component_name` | Name of the affected plugin or theme, or `null`. Always `null` for file and database findings. |
| `remediation` | `core_update_available`, `component_update_available`, `component_delete_available`, or `none` |

When `truncated` is `true`, more findings exist. Send `next_after_finding_ref` as `after_finding_ref` to get the next page. `revision` matches the results summary, so you can tell whether newer results arrived between pages.

The response never includes file paths, source URLs, or raw Jetpack data. If the site has no complete saved results, this ability returns `invalid_snapshot`. Request a refresh, or check the results summary first.

## Change Jetpack Connection

**Ability:** `mainwp/replace-site-jetpack-protect-connection-v1`<br />
**Method:** DELETE<br />
**Input:** `site_id_or_domain`, `desired_state`, `if_match`, `request_ref`, `dry_run`, and `confirm` (all required)

Previews or requests connecting or disconnecting Jetpack on one child site. `desired_state` is `connected` or `disconnected`. Disconnecting Jetpack can affect other Jetpack features on that site, so try this on a test site first.

Preview the change, using the `revision` from [Get Control State](#get-control-state) as `if_match`:

```bash
curl -X DELETE -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_id_or_domain":1,"desired_state":"disconnected","if_match":"dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd","request_ref":"11111111-1111-4111-8111-111111111111","dry_run":true,"confirm":false}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/replace-site-jetpack-protect-connection-v1/run'
```

**Example preview response:**

```json
{
  "mode": "preview",
  "request_ref": "11111111-1111-4111-8111-111111111111",
  "operation_ref": null,
  "site_id": 1,
  "would_change": true,
  "status": "preview",
  "current_state": "connected",
  "desired_state": "disconnected"
}
```

After reviewing the preview, send the same input with `"dry_run":false,"confirm":true`. Keep the same `if_match` and `request_ref`.

**Example confirmed response:**

```json
{
  "mode": "accepted",
  "request_ref": "11111111-1111-4111-8111-111111111111",
  "operation_ref": "22222222-2222-4222-8222-222222222222",
  "site_id": 1,
  "would_change": true,
  "status": "queued",
  "current_state": "connected",
  "desired_state": "disconnected"
}
```

| Field | Meaning |
|-------|---------|
| `mode` | `preview` or `accepted` |
| `operation_ref` | `null` for a preview. After confirmation, pass it to [Get Operation Status](#get-operation-status). |
| `would_change` | `false` when the site is already in the desired state |
| `status` | `preview`, `queued`, or `succeeded` |
| `current_state` | The connection state when the request was checked |
| `desired_state` | The state you asked for |

If the site is already in the desired state, a confirmed request returns `status: "succeeded"` with an `operation_ref` and sends nothing to the child site. To undo a change, read the control state again and request the opposite state with the new `revision`.

```json
{
  "mode": "preview",
```

## Request a Refresh

**Ability:** `mainwp/request-site-jetpack-protect-refresh-v1`<br />
**Method:** POST<br />
**Input:** `site_id_or_domain` and `request_ref` (both required)

Asks the Dashboard to fetch the current Jetpack Protect results from the child site in the background and save them. There is no preview step.

```bash
curl -X POST -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_id_or_domain":1,"request_ref":"44444444-4444-4444-8444-444444444444"}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/request-site-jetpack-protect-refresh-v1/run'
```

**Example response:**

```json
{
  "operation_ref": "55555555-5555-4555-8555-555555555555",
  "site_id": 1,
  "type": "refresh",
  "status": "queued",
  "accepted_at": "2026-10-31T09:05:00Z"

```

Follow the `operation_ref` with [Get Operation Status](#get-operation-status). When the refresh succeeds, read the new results with [Get Site Results Summary](#get-site-results-summary) and [List Site Findings](#list-site-findings).

## Get Operation Status

**Ability:** `mainwp/get-site-jetpack-protect-operation-v1`<br />
**Method:** GET<br />
**Input:** `site_id_or_domain` and `operation_ref` (both required)

Reads the current status of a refresh, connection, or visibility request. You can read only operations that you requested yourself, for the same site. Finished operation records are removed after about 7 days.

```bash
curl -G -u "${MAINWP_USERNAME}:${MAINWP_APPLICATION_PASSWORD}" \
  --data-urlencode 'input_json={"site_id_or_domain":1,"operation_ref":"22222222-2222-4222-8222-222222222222"}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/get-site-jetpack-protect-operation-v1/run'
```

**Example response:**

```json
{
  "operation_ref": "22222222-2222-4222-8222-222222222222",
  "site_id": 1,
  "type": "connection",
  "status": "succeeded",
  "accepted_at": "2026-10-31T09:01:00Z",
  "started_at": "2026-10-31T09:01:02Z",
  "finished_at": "2026-10-31T09:01:05Z",
  "outcome": "disconnected",
  "retryable": false
}
```

| Field | Meaning |
|-------|---------|
| `type` | `refresh`, `connection`, or `visibility` |
| `status` | See the table below |
| `started_at`, `finished_at` | `null` until the work starts or finishes |
| `outcome` | `observation_refreshed`, `connected`, `disconnected`, `visible`, `hidden`, `failed`, `outcome_unknown`, or `null` while the work is still running |
| `retryable` | `true` when a new request is safe |

| Status | Meaning | What to do |
|--------|---------|------------|
| `queued` | Waiting for the next scheduled task run | Check again later |
| `running` | The Dashboard is working on it | Check again later |
| `succeeded` | Finished as requested | Nothing |
| `failed` | Finished without making the change or refresh | Read the control state, then send a new request with a new `request_ref` |
| `unknown` | The result could not be confirmed. This is final. | Read the control state, then send a new request only if you still need the change |
| `expired` | Never started within an hour; nothing was sent to the child site | Check scheduled tasks on the Dashboard, then send a new request |

## Privacy and Redaction

All Jetpack Protect abilities return an explicit set of fields. They never return raw stored scan data, Jetpack account details, credentials, source URLs, or server file paths.

Before returning a response, the two stored summary abilities check every text value:

- Query strings and fragments are removed from URL-like text.
- Text containing a `Basic` or `Bearer` authentication marker is replaced with `[redacted]`. This also applies to site names and component names that contain these words followed by more text, such as `Basic Auth`.
- Common API keys, JWTs, PEM blocks, and `password=`, `token:`, or similar assignments are replaced with `[redacted]`.
- Text containing links, slashes, or `@` is returned as an empty string.
- Text values are limited to 200 characters.

This is a bounded masking policy, not a guarantee that any arbitrary string is safe to share.

The site abilities save and return only checked fields from the child site. Finding titles are limited to 160 characters and component names to 120. File and database findings never include a component name. Text with control characters or angle brackets is rejected, and results that fail these checks are not saved.

## Error Handling

Standard authentication, schema, and method errors follow the [Abilities API error reference](/api-reference/abilities-api/overview#error-reference). The two stored summary abilities return:

| Code | HTTP | Meaning |
|------|------|---------|
| `mainwp_permission_denied` | 401 or 403 | The request is unauthenticated, or the user lacks `manage_options` or access to the Jetpack Protect add-on |
| `mainwp_site_not_found` | 404 | The site ID does not exist or you cannot access it |
| `mainwp_jetpack_protect_read_failed` | 500 | The Dashboard could not read stored Jetpack Protect results. The error does not include database details. |

The eight site abilities return:

| Code | HTTP | Meaning |
|------|------|---------|
| `mainwp_protect_invalid_input` | 400 | A field is missing, has the wrong type, or both `dry_run` and `confirm` are `true` |
| `mainwp_permission_denied` | 401 or 403 | The request is unauthenticated, or the user does not pass the Dashboard's Abilities permission check |
| `access_denied` | 403 | The user cannot use the Jetpack Protect add-on |
| `mainwp_access_denied` | 403 | The user cannot access this site |
| `site_not_found`, `mainwp_site_not_found` | 404 | The site does not exist or is outside your allowed sites |
| `operation_not_found` | 404 | No operation with this reference exists for you on this site |
| `confirmation_required` | 409 | Both `dry_run` and `confirm` are `false` |
| `stale_revision` | 409 | `if_match` no longer matches the site's control state. Read it again. |
| `request_conflict` | 409 | This `request_ref` was already used with different input |
| `lock_busy` | 409 | A request of the same type is already in progress for this site |
| `contradictory_readback` | 409 | The child site could not confirm the new state after the change |
| `invalid_snapshot` | 422 | No complete saved results exist for findings, or the child site sent a control state that could not be checked |
| `unsupported_version` | 422 | MainWP Child on the site is older than 6.4 or does not support this request |
| `plugin_unavailable`, `unsupported_operation` | 422 | The child site cannot run this request, for example because Jetpack Protect is not available there |
| `invalid_request` | 400 | The child site rejected the request |
| `write_failed` | 500 | The child site could not save the change |
| `remote_unavailable` | 502 | The Dashboard could not reach the child site |
| `storage_unavailable` | 503 | The Dashboard could not read or save its records, or could not schedule the background task |

Errors reported by the child site return the code and status only, with no other detail. When a confirmed change ends with one of these codes while running in the background, the operation's status is `failed`. Any other unconfirmed result makes it `unknown`.
