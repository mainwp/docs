MainWP Dashboard 6.4 registers 32 abilities in the `mainwp-backups` category. Use them to manage [MainWP Built-In Backups](/sites/backups/manage-backups) through the WordPress Abilities API or the [MainWP MCP Server](/mcp-server/overview).

## Prerequisites

- MainWP Dashboard 6.4 or later and the matching MainWP Child release
- WordPress 6.9 or later on the Dashboard
- An authenticated Dashboard user with access to the requested sites and the required backup permissions
- Built-in backups enabled for backup creation and restores

Authenticate direct API requests with a [WordPress Application Password](/api-reference/rest-api/application-passwords). MainWP REST API keys do not authenticate Abilities API requests.

## Discover the Available Schemas

List the category to retrieve each ability's input schema, output schema, and execution instructions:

```bash
curl -u 'USERNAME:APPLICATION_PASSWORD' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities?category=mainwp-backups&per_page=50'
```

Fetch one ability's definition before calling it:

```bash
curl -u 'USERNAME:APPLICATION_PASSWORD' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/run-site-backup-v1'
```

Use the returned schema for the installed Dashboard version. Inputs reject unknown fields. Storage credentials, encryption keys, and recovery passphrases are not exposed by these abilities.

## Read Backup Status

Read abilities use `GET`. Pass input as a JSON-encoded `input` query parameter when needed:

```bash
curl -G -u 'USERNAME:APPLICATION_PASSWORD' \
  --data-urlencode 'input={"site_id_or_domain":1}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/get-site-backup-progress-v1/run'
```

| `mainwp/get-backup-destination-v1` | Read one destination without its credentials |
| `mainwp/get-backup-settings-v1` | Read backup settings without recovery secrets |

## Preview and Confirm Changes

Write abilities use `POST` and require either `dry_run: true` to preview or `confirm: true` to execute. Preview the action, review its affected sites, destinations, retention deletions, and warnings, then confirm the same selection. Do not set both flags to true.

For example, preview an on-demand full backup:

```bash
curl -X POST -u 'USERNAME:APPLICATION_PASSWORD' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_id_or_domain":1,"dry_run":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/run-site-backup-v1/run'
```

After reviewing the preview, execute it:

```bash
curl -X POST -u 'USERNAME:APPLICATION_PASSWORD' \
  -H 'Content-Type: application/json' \
  -d '{"input":{"site_id_or_domain":1,"confirm":true}}' \
  'https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/run-site-backup-v1/run'
```

The backup continues in the background. Follow the returned polling instructions until it completes or fails. A start response does not mean the backup has finished. If the result is `not_started`, no work was queued; retry later. An `already_running` result attaches to an existing run, so poll it rather than starting another.

## Permissions and Restore Results

Abilities enforce the user's site access, task ownership, and operation permissions. Storage changes require an account with access to all sites. Reading or changing global backup settings requires the corresponding Dashboard settings permissions.

Before confirming a restore, review the preview's replacement and WooCommerce warnings. After starting it, poll `mainwp/get-restore-job-v1` and inspect `outcome`, `partial_state_risk`, and `verification`. A cancellation request may still be pending; keep polling until the site confirms it stopped. Rollback requires an available safety backup from the original restore.

For restore precautions and recovery options, see [Restore a Snapshot](/sites/backups/manage-backups#restore-a-backup).
