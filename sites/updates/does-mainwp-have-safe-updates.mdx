A Safe Update checks each site, backs it up if your backup settings require it, applies the updates, and checks the site again. When a check fails after the update, you can roll the plugin or theme back to its previous version, or let MainWP re-apply the updates one at a time to find the one that caused the failure.

Safe Updates is part of MainWP Dashboard and needs no add-on. The plain **Update** buttons still work as before; **Safe Update** sits beside them.

## What You'll Accomplish

- Start a checked update run from the Updates page or Manage Sites
- Choose which checks run before and after updating
- Follow a run and find the sites that need attention
- Roll back a plugin or theme update, or find which update broke a check
- Run automatic updates with the same checks
- Use Safe Updates from the Abilities API and in Pro Reports

## Prerequisites

- MainWP Dashboard X or later
- An update right for the item types you want to update (**Update Plugins**, **Update Themes**, **Update Translations**, or **Update WordPress**)
- For rollback: child sites running WordPress 6.3 or later and MainWP Child X or later
- For a backup before updating: [Built-In Backups](/sites/backups/manage-backups) with **Require a backup before an update** turned on
- For the Regression test check: the [Regression Testing](/add-ons/security/regression-testing-extension) add-on, version X or later, on a Dashboard running WordPress 6.9 or later

Updates and site checks use the same requests as ordinary updates and work with current MainWP Child versions. Only rollback needs MainWP Child X.

## Start a Safe Update

### From the Updates Page

<Steps>
<Step title="Open Updates">
Go to **MainWP > Updates** and open the **Plugins**, **Themes**, **WordPress**, or **Translations** tab.
</Step>
<Step title="Select updates">
Tick the rows you want to update. If you tick nothing, the run includes every update on the tab.
</Step>
<Step title="Click Safe Update">
Click **Safe Update** (green, with a shield icon) beside the update buttons. The **Safe Update** preview opens. Nothing changes on your sites until you confirm.
</Step>
<Step title="Review the preview">
Choose the checks under **Checks to run before and after updating**, then review each site's updates, backup status, and checks.
</Step>
<Step title="Start the run">
Click **Start Safe Update**. The run page opens. You can close it; the run keeps going.
</Step>
</Steps>

<Note>
Screenshot to add: Updates page, Plugins tab, with the **Safe Update** button beside the update buttons. Dark theme.
</Note>

The selection follows the Updates page view, so it includes live sites or staging sites depending on which view is open.

### From Manage Sites

Go to **MainWP > Sites > Manage Sites**, tick the sites, choose **Safe Update Everything** from the bulk actions, and click **Apply**. The run includes every pending update on the selected sites. The same preview opens before anything starts.

</Note>

### The Preview

The preview lists each site with its **Updates** (name and version change), **Backup**, and **Checks**.

All three checks are on by default:

- **HTTP check**
- **Uptime monitors**
- **MainWP Child responds**

Untick a check to leave it out of the run. The preview then shows it as **Not selected**.

The **Backup** column shows what happens before the site is updated:

| Label | Meaning |
|-------|---------|
| **Recent backup** | A backup within your tolerance exists. The update goes ahead. |
| **Will back up first** | No recent backup. The run starts one and waits for it. |
| **Waits for the offsite copy** | A recent local backup is still uploading to remote storage. The run waits for it. |
| **Will update without a recent backup** | You ticked the override below. |
| **Not required by settings** | Your settings do not require a backup for this site. |

When a selected site has no recent backup, the preview shows **Update sites that have no recent backup without waiting for one**. Ticking it applies to every site in the run.

Sites marked **Suspended, will be skipped** or **Already in a run, will be skipped** are left out. A site can be in only one Safe Updates run at a time. If some sites were already in another run when you started, the message lists them with an **Open run** link.

## What Happens on Each Site

Each site goes through these steps in order. The site's row on the run page shows the current step.

1. **Checking before update**: the selected checks run once to record how the site behaves now.
2. **Backing up**: only when your settings require a backup (see [Backups Before Updating](#backups-before-updating)).
3. **Updating**: MainWP sends the updates in small groups, using the same update requests as the Updates page. The backup requirement is checked again just before sending.
4. **Waiting before checks**: the run waits 60 seconds after the site's last update.
5. **Checking after update**: the same checks run again. A check that fails or times out is retried once, 3 minutes later. The row shows **Retrying in 3 minutes**.

If the run cannot tell whether an update finished (for example, the request timed out), it syncs the site and compares the installed version instead of sending the update again. After 5 minutes without an answer, the item fails with **No result from the site**. The run never sends the same update twice.

A site that is deleted or suspended during the run is skipped.

Updates started elsewhere on the same site, such as from the plain **Update** buttons or automatic updates, are not blocked. While a site is in a run, those updates skip the **Check site HTTP response after update** check so the site is not checked twice.

## Site Checks

| Check | What it does |
|-------|--------------|
| **HTTP check** | Loads the site's home page, allowing 10 seconds for the whole redirect chain. It uses the same "up" status codes as [Uptime Monitoring](/sites/management/uptime-monitoring): the site's own monitor settings if it has a primary monitor, otherwise the global list. The result shows the status code and time, for example `200 in 0.8 s`. |
| **Uptime monitor** | Runs one check for each monitor already set up for the site. Keyword monitors also look for the keyword and report **keyword found** or **keyword not found**. These checks do not record heartbeats, create incidents, or send monitor alerts. |
| **MainWP Child** | Asks MainWP Child on the site to answer a sync request within 10 seconds. Nothing from the answer is saved. |
| **Regression test** | Runs after updating only. It reads the post-update scan from the Regression Testing add-on and compares it with the site's saved baseline. A change above the site's threshold fails the check. |

The Regression test check appears only when the Regression Testing add-on supports it. It waits for the scan for the site's scan delay plus 15 minutes, up to 60 minutes, then reports **scan did not finish in time** with a link to the add-on's page for the site. When it cannot run, it says why, for example **no baseline yet** or **post-update scans disabled**.

### Check Results

Each check shows its result before and after the update, with one line of evidence. When the two differ, the row shows **Before:** and **After:** lines.

| Result | Icon | Effect on the site |
|--------|------|--------------------|
| Pass | Green check | None |
| Fail | Red cross | The site **Needs attention** if the check passed before the update |
| Slow | Yellow clock | Shown, but the site does not need attention |
| Not run | Grey minus | Shown with the reason, for example **No monitor configured**. The site does not fail. |
| Pending | Blue spinner | The check has not finished yet |

A check that failed before the update and still fails afterward is labelled **Failing before this run**. The update did not cause it, so the site result stays **OK** with that note. A Regression test result is never labelled this way.

## Backups Before Updating

Safe Updates uses the same backup requirement as other updates. It applies only when all of these are true:

- Built-In Backups is turned on.
- **Require a backup before an update** is on in **MainWP Settings > General Settings > Updates Settings**.
- The site's own **Require backup before update** setting is not **No**.

Otherwise the **Backup** column shows **Not required by settings**.

When the requirement applies, the run checks for a backup within **Days without a full backup (tolerance)**, and with **Require an offsite-verified backup** on, a verified remote copy:

- **Recent backup**: the update goes ahead.
- **Waiting for the offsite copy**: a recent local backup is still uploading. The run waits and does not start another backup.
- **No recent backup**: the run starts one full backup and waits for it.

The run waits up to 30 minutes from the start of the backup step. If the backup has not finished by then, the site is skipped with **Backup did not finish**. If the backup cannot start, the site is skipped with the reason. Other sites in the run continue.

When the backup requirement applies to a selected site, starting the run needs the **Execute Backups** right. With the override ticked, the run does not back up, so that right is not needed, and the **Backup** column shows **Updated without a recent backup**.

See [Require a Backup Before Updates](/sites/backups/manage-backups#require-a-backup-before-updates) for the settings.

## Follow a Run

### Run List

Go to **MainWP > Updates > Safe Updates** to see all runs. Filter them with **All runs**, **Manual**, or **Automatic updates**, or click **Go to Updates** to start a new one.

| Column | Shows |
|--------|-------|
| **Run** | A link to the run page |
| **Started** | When the run started and who started it. Automatic runs show **Schedule**. |
| **Source** | **Manual** or **Automatic updates** |
| **Status** | **Running**, **Stalled**, **Cancelling**, **Done**, or **Cancelled** |
| **Sites** | Number of sites in the run |
| **Results** | Site counts by result |

The status label is blue while a run is running, stalled, or cancelling, and grey when it was cancelled. A finished run is orange when any site needs attention or failed, and green otherwise.

Runs older than 12 months are deleted automatically.

<Note>
Screenshot to add: Safe Updates run list with one manual run and one automatic updates run. Dark theme.
</Note>

### Run Page

The run page shows who started the run and when, a progress bar (**N of M sites finished**), and site counts: **OK**, **Needs attention**, **Resolved**, **Failed**, **Skipped**, and **In progress**.

The site table has the columns **Site**, **Result**, **Updates**, **Backup**, and **Checks**, plus row actions. Use **All sites** and **Needs attention** to filter the table, and **All runs** to go back to the list.

The page refreshes every 5 seconds while it is open.

<Note>
Screenshot to add: run page while a run is in progress, with rows showing step labels such as **Checking before update** and **Updating**, and the progress bar. Dark theme.
</Note>

### Site Results

| Result | Meaning |
|--------|---------|
| **OK** | Updated, and the checks passed (or a check was already failing before the run) |
| **Partly updated** | OK, but some items were not updated. The row shows how many. |
| **Needs attention** | Updated, and a check that passed before the update now fails |
| **Resolved** | Needed attention, then was rolled back or marked as expected |
| **Failed** | An update failed, the site stopped responding, or the person who started the run lost access |
| **Skipped** | Not updated, with the reason, for example **Cancelled** or **Backup did not finish** |

The **Needs attention** filter lists sites that need attention, failed, or were skipped (except cancelled sites), and any finished site with items that were not updated.

### Item States

Each update on a row has its own state:

| State | Meaning |
|-------|---------|
| **Updated** | Installed |
| **Rolled back** | Returned to its previous version |
| **Failed** | The update failed |
| **License blocked** | The update package was not available, usually because of a license or download problem. This is not counted as a broken site. |
| **Reverted by WordPress** | The install failed and WordPress put the old version back (see [When an Update Fails to Install](#when-an-update-fails-to-install)) |
| **Sent, waiting for the result** | Sent to the site, result not confirmed yet |
| **Not updated** | Not sent, for example because the run was cancelled |

### Cancel a Run

Click **Cancel run** on the run page. Sites that have not been updated yet are skipped. An update already sent to a site finishes and is checked.

Only the person who started the run, or someone who manages every site in it, can cancel it. Automatic update runs cannot be cancelled.

## Fix a Site That Needs Attention

Row actions appear when a site's row has finished.

| Action | What it does | When it appears |
|--------|--------------|-----------------|
| **Retest** | Runs the after-update checks again without updating anything. The site becomes **OK** or stays **Needs attention**. | On a **Needs attention** row, including one marked as expected, unless it was rolled back |
| **Mark as expected** | Keeps the result but takes the site off the **Needs attention** list. Nothing is updated or rolled back. | On a **Needs attention** row |
| **Roll back** | Returns one plugin or theme to its previous version | On each updated plugin or theme that can be rolled back |
| **Roll back all updates from this run** | Returns every plugin and theme this run updated on the site to its previous version | When two or more updated plugins or themes on the row can be rolled back |
| **Find the cause** | Re-applies the rolled-back updates one at a time with a check after each. Only an update that fails the check stays rolled back. | After **Roll back all updates from this run** made the failing checks pass, with at least two items rolled back |
| **Open site** | Opens the site in a new tab | On finished rows |
| **Restore backup** | Opens **Snapshots & Restore** for the site | When Built-In Backups is on and you have the **Execute Backups** and **Restore Backups** rights |

## Roll Back an Update

<Warning>
Rollback replaces the plugin or theme files only. Database changes made by the new version are not undone. If the new version changed the database, restore a backup instead.
</Warning>

<Steps>
<Step title="Open the run">
Open the run from **MainWP > Updates > Safe Updates** and find the site's row.
</Step>
<Step title="Choose what to roll back">
Click **Roll back** on one item, or **Roll back all updates from this run** for every plugin and theme the run updated on the site.
</Step>
<Step title="Confirm">
Read the confirmation and confirm. When **Restore backup** is available, the confirmation links to it.
</Step>
<Step title="Review the result">
The checks run again after the rollback. The row shows **Rolled back and checked**, or **Rollback did not fix the check. Review the site or restore backup.**
</Step>
</Steps>

<Note>
Screenshot to add: the same site row after rollback, showing **Rolled back**, the message **Rolled back and checked**, and passing checks. Dark theme.
</Note>

### What Rollback Can Undo

MainWP Child keeps the previous version of each plugin or theme it updates, one version per item, for 14 days. The copy is kept in a protected folder on the child site. Rollback swaps that copy back in, keeps the item's activation state, and puts the new version back if the swap fails.

Rollback is available for plugins and themes. For WordPress core and translations, use **Restore backup**.

When **Roll back** is not available, the item says why:

| Reason | Meaning |
|--------|---------|
| **Needs MainWP Child X** | The child site runs an older MainWP Child |
| **Needs WordPress 6.3** | The child site runs WordPress older than 6.3 |
| **Kept version expired** | More than 14 days have passed |
| **Replaced by a later update** | The item was updated again after this run |
| **Low disk space** | The site had less than 100 MB free when it updated, so no copy was kept. The update itself went ahead. |
| **Not available for this item** | WordPress core and translation updates |

You need the same right to roll back an item as to update it (**Update Plugins** or **Update Themes**).

### Held Versions

After a rollback, the rolled-back version is held on that site. The Updates page shows the rollback icon beside it right away, with the tooltip "This version failed a previous update and was rolled back. Proceed with caution." Automatic updates skip that version and older ones on that site until a newer version is offered.

### Find the Cause

When **Roll back all updates from this run** makes the failing checks pass, **Find the cause** works out which update was responsible:

1. The rolled-back updates are re-applied one at a time.
2. After each one, the checks run again.
3. An update that passes stays updated. An update that fails is rolled back again and held.

When it finishes, the row names the update that caused the failure, for example "Sample Plugin caused the failed check and stays rolled back." If no single update fails, the row says "No single update failed the check. All updates were re-applied."

If **Roll back all updates from this run** does not fix the checks, **Find the cause** is not offered. Review the site, or restore a backup.

## Check Automatic Updates

Two settings in **MainWP Settings > General Settings > Updates Settings** apply Safe Updates to [automatic updates](/sites/updates/manage-updates):

- **Safe Updates: check sites before and after automatic updates** (Default: on). Each automatic update pass that updates something creates one Safe Updates run, with the source **Automatic updates** and **Schedule** as the starter. When this is off, automatic updates and their email work as they did before.
- **Safe Updates: roll back automatically when a check fails** (Default: off). Rolls back plugin and theme updates on a site when a check fails after an automatic update.

Changes to these settings apply from the next automatic update pass.

Automatic runs always use every check: HTTP, uptime monitors, MainWP Child, and Regression test when available. Your automatic update schedule, delay, and backup rules stay the same. A site that is already in a manual run is skipped by that automatic pass. If the pass ends before a site is updated, the site is skipped with the reason.

### Automatic Rollback

With automatic rollback on, a rollback starts only when the HTTP, Uptime monitor, or MainWP Child check passed before the update and fails after it. A Regression test result never starts one.

MainWP rolls back the plugin and theme updates on that site that can be rolled back, and checks the site again. If that fixes the site, it runs [Find the cause](#find-the-cause) so only the responsible update stays rolled back and held.

## Summary Email

MainWP sends one summary email when a run finishes. Unlike the older automatic updates email, it includes failed and skipped sites.

- **Manual runs** use **Safe Updates Email** in **MainWP Settings > Email Settings**. It is on by default, with the subject "Safe Updates summary".
- **Automatic runs** use the **Auto Updates Email** on/off switch and recipients, with the Safe Updates content. You get one email per automatic update pass.
- With **Safe Updates: check sites before and after automatic updates** off, automatic updates send the older **Auto Updates Email**, which lists successful updates only.

The email shows result counts, lists each site that needs a person with its result and reason, links to the run with **View run**, and then lists each site's items with their old version, new version, and status. A cancelled or stalled run adds "Cancelled: " or "Stalled: " to the start of the subject.

You can customize the template like other MainWP email templates. See [Email Settings](/sites/management/mainwp-dashboard-settings#manage-email-notifications).

## Stalled Runs and Slow Hosting

Runs move forward on a WP-Cron event that runs every minute, on server cron if you use it, and while a run page is open. You can close the browser once a run starts.

If you run MainWP from server cron, the existing `updatescheck.php` job also moves Safe Updates runs, so you do not need a new cron line. A separate `safeupdates.php` worker is available. See [Disable WP-Cron](/customization/disable-wp-cron).

### Stalled Runs

A run that makes no progress for 10 minutes is marked **Stalled**. This usually means WP-Cron is not running on your Dashboard. Other MainWP pages show the notice **A Safe Update run has stalled** with an **Open run** link.

Open the run. It keeps moving while the run page is open, and **Continue** moves it on by one step.

<Note>
Screenshot to add (optional): run page for a stalled run, showing the yellow message and the **Continue** button. Dark theme.
</Note>

### What Happens on Slow Hosting

- A slow or interrupted request loses only the step in progress. The next pass picks up from the last saved step, and finished checks are kept.
- A site that stops responding three times in the same step fails with **Stopped responding while** and the step name. The run continues with the other sites.
- A check that times out shows as slow, not failed.
- A backup that does not finish within 30 minutes skips only that site.
- A child site with less than 100 MB free still updates, but rollback is not available for that update.

The run adds no work to ordinary Dashboard page loads. Your existing settings for simultaneous requests and delays still apply.

## Who Can Run Safe Updates

Safe Updates adds no new Team Control rights. It uses the existing ones:

| Right | Allows |
|-------|--------|
| Any update right | See **Safe Updates**, open runs, and use **Retest**, **Mark as expected**, and **Continue** |
| **Update Plugins**, **Update Themes**, **Update Translations**, **Update WordPress** | Start a run for that item type. **Update Plugins** and **Update Themes** also allow rollback. |
| **Execute Backups** | Start a run on sites where the backup requirement applies, unless you tick the override |
| **Execute Backups** and **Restore Backups** | Show **Restore backup** |

Users with access to some sites see only runs that include their sites, and only their sites' rows. A run is checked against the rights of the person who started it at every step. If that person loses access, the remaining sites fail with **access revoked**.

See [Team Control](/add-ons/agency/team-control-extension) for roles and rights.

## When an Update Fails to Install

Separately from Safe Updates, MainWP uses the WordPress rollback that runs when a plugin or theme update fails to install. WordPress keeps the current version while it installs the new one, and puts it back if the install fails. This works on child sites running WordPress 6.3 or later, on every page where you can start updates. In a Safe Updates run, such an item shows **Reverted by WordPress**.

This only covers a failed install. If the update installs but breaks the site, use a Safe Update rollback or restore a backup.

## Restore a Site Backup

Use [MainWP Built-In Backups](/sites/backups/manage-backups) to restore a site's files, database, or both. On a run page, **Restore backup** opens **Snapshots & Restore** for that site. Choose a snapshot with the backup type you need. Changes made after that snapshot may be lost.

A restore also undoes database changes, which rollback cannot. For an item that cannot be rolled back, you can also install an earlier version by hand with [Install by Upload](/sites/plugins/managing-plugins-with-mainwp#install-by-upload).
