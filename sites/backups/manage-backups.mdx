MainWP Built-In Backups lets you back up and restore Child Sites directly from MainWP Dashboard, without a backup add-on or third-party backup plugin.

MainWP Child creates the backup archive. Your MainWP Dashboard downloads it, stores it locally, and uploads copies to the selected storage destinations. Backups do not upload directly from the Child Site to cloud storage.

<Info>
MainWP Built-In Backups is available in MainWP 6.4 and later. Keep MainWP Dashboard and MainWP Child updated, and test backups and restores on a staging site.
</Info>

To manage your hosting provider's backups, use [API Backups](/sites/backups/api-backups). For third-party backup plugins, see [Backup Add-ons](/add-ons/backups).

## What You'll Learn

- Create your first backup and confirm where it is stored
- Schedule full, database, files-only, and incremental backups
- Connect storage destinations and protect backups with encryption
- Restore a site and roll back using a safety backup
- Manage retention and investigate failed jobs

## Prerequisites

- MainWP Dashboard 6.4 running PHP 8.3 or higher
- MainWP Child with built-in backup support, running PHP 7.4 or higher
- A connected Child Site that syncs successfully
- An administrator account to enable and configure backup settings
- Enough free disk space on the Child Site and Dashboard for backup and restore files
- Working WordPress cron on the Dashboard for schedules and background tasks
- Storage credentials if you want copies outside the Dashboard

Keep a separate backup of your MainWP Dashboard installation, including its database and backup encryption keys.

## Find the Backup Screens

Open **MainWP > Sites > Backups** after enabling built-in backups.

| Screen | Use it for | Relative URL |
| --- | --- | --- |
| Top-right user menu > MainWP Settings > Backup Settings | Enable built-in backups, encryption, diagnostics, and on-demand retention | `/wp-admin/admin.php?page=BackupSettings` |
| Backups > Manage Backups | View schedules, run tasks, and inspect errors | `/wp-admin/admin.php?page=ManageBackups` |
| Backups > Add New | Create a scheduled backup task | `/wp-admin/admin.php?page=ManageBackupsAddNew` |
| Backups > Storage | Connect and test storage destinations | `/wp-admin/admin.php?page=ManageBackupsStorage` |
| Backups > Snapshots & Restore | Create an on-demand backup, download, restore, or clean up snapshots | `/wp-admin/admin.php?page=ManageBackupsSnapshots` |

A **task** defines what to back up, which sites to include, and when to run. A **snapshot** is a backup of one site at a particular time. One task can create snapshots for several sites.

## Create Your First Backup

<Steps>
<Step title="Enable built-in backups">
Open **top-right user menu > MainWP Settings > Backup Settings** (`/wp-admin/admin.php?page=BackupSettings`).

If **Select primary backup system** is shown, select **Built-In Backups**. Turn on **Enable Built-In Backups** and click **Save Settings**.
</Step>

<Step title="Choose where to store the backup">
The backup stays on your Dashboard server unless you add another destination.

For an additional copy, open **Backups > Storage**, add and test a destination, and select **Use as default destination**. See [Configure Storage](#configure-storage).
</Step>

<Step title="Select the site and start the backup">
Open **Backups > Snapshots & Restore** (`/wp-admin/admin.php?page=ManageBackupsSnapshots`) and select your test site.

Read the destination message, then click **Back Up Now**. This creates a full backup. To run a different backup type, create a task and use **Run Now** instead.

![Snapshots & Restore in dark mode, with the selected site, backup destinations, Back Up Now button, and existing snapshots.](/images/sites/built-in-backups/snapshots-and-restore.jpg)
</Step>

<Step title="Confirm the result">
Wait for the backup to finish and confirm that a new snapshot appears with the expected date, type, and size. Review any **files not backed up** warning before relying on the backup.

If you selected remote storage, wait for the upload to finish. See [Check Backup Status](#check-backup-status).
</Step>
</Steps>

<Note>
**Back Up Now** uses the destinations selected on the site's scheduled tasks. If those tasks have no destinations, the backup stays on the Dashboard. The default destination applies only to sites without a scheduled task.
</Note>

## Configure Storage

Completed backups are stored in the Dashboard's private backup directory, organized by Child Site. Storage destinations receive copies uploaded by the Dashboard. A **Local Path** destination also refers to a path on the Dashboard server. Keep enough free space on both the Dashboard and Child Site to create and process backups, even when using [Remove local archives after upload](#retention-and-cleanup).

When moving the Dashboard, [include its private backup directory in the transfer](/advanced/how-to-migrate-the-mainwp-dashboard#preserve-built-in-backup-files).

<Steps>
<Step title="Add a destination">
Open **Backups > Storage** (`/wp-admin/admin.php?page=ManageBackupsStorage`) and click **Add Storage Destination**. Enter a descriptive **Destination name**, then choose a **Provider**.
</Step>

<Step title="Enter the provider details">
Enter the details listed below for your provider. The account needs permission to upload, read, and delete backup files at that destination.

![Add Storage Destination form with S3 Compatible Storage selected and example destination and bucket names.](/images/sites/built-in-backups/storage-destination.jpg)
</Step>

<Step title="Test and save">
Click **Test Connection & Save**. Resolve any connection error before assigning the destination to a backup task.

For Dropbox, use **Connect Dropbox** to approve the connection. A successful connection tests and saves the destination.
</Step>

<Step title="Assign the destination">
On each backup task, select one or more destinations under **Upload to storage**.

Choose **Use as default destination** or **Make Default** to preselect a destination for new tasks. Update existing tasks separately if you want them to use it.
</Step>
</Steps>

| Provider | Details to enter |
| --- | --- |
| S3 Compatible Storage | Bucket, Region, Access key, and Secret key. Leave Endpoint empty for Amazon S3; enter your service's endpoint for other S3-compatible storage. Enable Path style addressing when your service requires it. |
| Google Cloud Storage | Bucket, HMAC access key, and HMAC secret from your storage interoperability settings. |
| Dropbox | App key, App secret, and an optional Folder. Register the exact Redirect URI shown in MainWP in your Dropbox app, then use Connect Dropbox. The app needs `files.content.write`, `files.content.read`, and `files.metadata.read` permissions. |
| SFTP | Host, Port, Username, and an existing absolute Directory path. Use a Password or a PEM Private key. When a private key is supplied, Password is its passphrase. |
| Local Path | An absolute Directory path on the Dashboard server, such as a mounted storage directory. It must be writable by the Dashboard. |

For SFTP, you can supply the server's **Host key fingerprint** to verify its identity. If left empty, the first key received is trusted and pinned. Obtain the fingerprint from your server administrator when possible.

**Local Path** does not count as offsite storage, even on a mounted drive, and cannot satisfy **Require an offsite-verified backup**.

Set **Minimum retention (days)** on a destination to protect its copies from automatic cleanup for a minimum period. The default is zero, which disables this protection. See [Minimum Retention at a Destination](#minimum-retention-at-a-destination).

### Share a Bucket Between Sites

You can use one private Amazon S3 or Backblaze B2 bucket for multiple Child Sites connected to the same MainWP Dashboard. For B2, select **S3 Compatible Storage** and enter the bucket's S3-compatible endpoint.

MainWP stores each site's snapshots under separate paths in the bucket. The Dashboard uploads the backups and keeps the storage credentials; it does not send those credentials to Child Sites. Sharing a destination does not give a Child Site permission to browse or download another site's backups.

For eligible restores of unencrypted backups, the Dashboard can send the Child Site temporary download links for the required backup files. These links expire after one hour and grant access only to the specified files. Encrypted backups are downloaded and decrypted on the Dashboard before being transferred to the Child Site.

Keep the bucket private and do not share its credentials with Child Sites. Separate paths organize the backups but do not create independent storage permissions. Anyone with bucket-wide access can access the backups, and anyone with a temporary download link can use it while it remains valid.

### Encrypt Backup Archives

Open **top-right user menu > MainWP Settings > Backup Settings** (`/wp-admin/admin.php?page=BackupSettings`):

1. Turn on **Encrypt backup archives** to show the **Backup recovery passphrase** fields.
2. Set a recovery passphrase. The first setup also asks for your WordPress password. Use at least 12 characters; a long, unique passphrase of 20 characters or more is recommended. Store it separately from the Dashboard.
3. Click **Save Settings** and confirm that encryption remains enabled.

![Backup Settings with archive encryption enabled and fields for the current and new recovery passphrases.](/images/sites/built-in-backups/backup-encryption.jpg)

MainWP encrypts new archives before uploading them. Existing snapshots remain unchanged. To change the recovery passphrase, enter the current and new passphrases. Leave the fields blank to keep the existing passphrase.

<Warning>
Keep the recovery passphrase and your Dashboard's encryption keys safe. The passphrase can recover a lost encryption key, but you still need backups of the Dashboard database and backup files.
</Warning>

S3 **Server-side encryption** encrypts the stored copy at the provider. You can use it alongside MainWP's archive encryption.

## Create a Scheduled Backup

Open **Backups > Add New** (`/wp-admin/admin.php?page=ManageBackupsAddNew`).

<Steps>
<Step title="Name the task and select its sites">
Enter a **Backup task name** that describes its purpose, such as "Daily client sites". Select the Child Sites to include.
</Step>

<Step title="Choose the backup type and schedule">
Select a **Backup type** from the table below. Choose **Daily**, **Weekly**, **Monthly**, or **Every N hours**.

Times use the Dashboard WordPress site's timezone. Monthly schedules accept days 1 through 28. Leave the optional time empty to run the task at the next scheduler check after its interval has elapsed.
</Step>

<Step title="Choose storage, exclusions, and retention">
Select destinations under **Upload to storage**, review **Backup Excludes**, and set **Backup Retention**.

Leave storage empty to keep backups only on the Dashboard. Set retention limits to control storage use.
</Step>

<Step title="Save and run a first test">
Click **Schedule Backup**. On **Manage Backups**, click **Run Now** for the task to test its configured type and destinations.

Check the result for each site, then confirm the task's **Next Run**.
</Step>
</Steps>

![Scheduled backup form configured for daily full backups at 02:00, with three sites and offsite SFTP storage selected.](/images/sites/built-in-backups/scheduled-backup.jpg)

### Choose a Backup Type

| Type | What it contains | Restore behavior |
| --- | --- | --- |
| Full Backup | Site files and database, subject to exclusions | Restores files and database |
| Database Backup | Database content, such as posts, settings, and users | Restores the database without replacing files |
| Files Only Backup | Site files without the database, subject to exclusions | Restores files while keeping the current database, when the Child Site supports files-only restore |
| Incremental Backup | A full first backup, then changed files and a fresh database dump on each later run | Reconstructs the selected point in time using its backup chain |

An incremental **chain** includes the initial full backup and the later incremental backups that depend on it. Keep the chain together so MainWP can restore the selected snapshot.

The first incremental task run is full even when started with **Run Now**. If a Child Site lacks incremental support, MainWP takes full backups and records a note on the task. Keep MainWP Child updated and sync the site after updating.

### Database and Disk Usage

Built-in backups use database space for task and snapshot records, and disk space for backup files and file inventories. Incremental tracking does not create a database row for every site file.

| Location | What is stored |
| --- | --- |
| Child Site database | Backup and restore task status, progress, and information needed to resume interrupted work |
| Child Site disk | Backup archives, working files, and the file inventory used for incremental comparisons, including file paths, sizes, and modification times |
| Dashboard database | Snapshot records, links between incremental snapshots, archive details, storage settings, upload and restore progress, upload chunk details, and run history |
| Dashboard disk | Downloaded backup archives and file inventories, plus working files used during transfers and restores |

Database usage varies with backup frequency, the number of snapshots and storage destinations, archive and upload chunk counts, and restore activity. There is no fixed database-space figure per site or backup.

Retention removes backup files and their associated upload records, but keeps snapshot records so removed backups can appear in the removal history. Background cleanup removes run history older than 90 days. The **Storage cap (MB)** setting applies to backup files; it does not set a database size limit.

### Archive Format and Exclusions

**Archive type** can use the site setting, the global setting, or an explicit format. The available formats are Zip, Tar, Tar GZip, and Tar BZip2.

For large sites, use **Tar GZip**. MainWP can switch large Zip backups to Tar GZip unless **Keep Zip even when the site is large** is enabled.

Review the exclusion switches for known backup locations, known cache locations, non-WordPress folders, and ZIP archives. Excluding old backup archives avoids repeatedly backing up earlier backups. Do not exclude files you expect to recover.

Enter **Custom excludes** as paths relative to the Child Site's WordPress directory, separated by newlines or commas. For example, `wp-content/cache`. To exclude the standard WordPress uploads folder, use `wp-content/uploads`. To exclude only a form upload folder, enter that folder's actual relative path. Excluded files will not be available from that backup during restore.

### Database Dumps and the Clone Folder

The database portion of a backup contains a separate `.sql.php` file for each table. Each file starts with `<?php exit(); ?>`, followed by SQL. The `.php` extension allows a PHP-enabled web server to run this guard and stop before displaying the database contents if the file is requested over HTTP. MainWP reads this format automatically during a restore.

In a full backup archive, the database dump files are placed under `wp-content`. This location is part of MainWP's archive format. There is no setting to move them to the archive root or another subfolder.

The `clone` folder contains `config.txt`, which holds metadata used by MainWP's backup/cloning format, including the original site URLs, WordPress path, database table prefix, and lists of plugins and themes. Built-in file restores skip this metadata file.

### Performance on Larger Setups

Backup work uses resources on both the Child Site's server and the MainWP Dashboard. The Child Site creates the database dump and archive. The Dashboard downloads and stores the backup, encrypts it when enabled, and uploads copies to the selected storage destinations. Remote storage still requires disk space and transfer bandwidth on the Dashboard.

Completion times depend on database size, file count, archive size, server resources, and transfer speeds. Site count alone does not determine the resources your setup needs.

- Create separate scheduled tasks for groups of sites and give them different start times. Spread backups throughout the day, especially for sites that share a server.
- Start with a small, representative group that includes a larger site. Check backup and upload completion times, server load, free disk space, and bandwidth use on the Dashboard and Child Site servers before expanding to more sites.
- Consider [incremental backups](#choose-a-backup-type) to reduce the file data saved after the initial full backup. Each run still includes a fresh database dump.
- Review [archive formats and exclusions](#archive-format-and-exclusions) to avoid repeatedly archiving caches, old backups, and other folders you do not need to recover. Use [retention limits](#retention-and-cleanup) to control storage use.

Keep [Dashboard cron](/customization/manage-wp-cron-on-low-traffic-mainwp-dashboard) working so scheduled backups and background uploads can continue. Check that both backup creation and storage uploads finish within the time available before the next run.

## Check Backup Health

View **Backup Health** in **MainWP > Sites > Manage Sites** (`/wp-admin/admin.php?page=managesites`) or **MainWP > Operations** (`/wp-admin/admin.php?page=mainwp_tab`). The summary appears when built-in backups are enabled and your account has permission to run backups.

<img src="/images/sites/built-in-backups/backup-health.jpg" alt="Backup Health widget with counts for Protected, At Risk, Critical, and No Backup." width="390" />

Each site is classified using its latest completed built-in backup snapshot:

| Status | Meaning |
| --- | --- |
| Protected | The snapshot is no more than 24 hours old and its offsite copies are verified. |
| At Risk | The snapshot is over 24 hours old but no more than 7 days old, or is no more than 24 hours old without verified offsite copies. |
| Critical | The latest completed snapshot is more than 7 days old. |
| No Backup | No completed built-in backup snapshot is recorded. |

Click a status to filter Manage Sites to the matching sites. For **At Risk**, check the backup schedule and storage uploads. For **Critical** or **No Backup**, run a backup and confirm it completes.

A recent backup stored only locally shows **At Risk**. **Protected** confirms backup age and offsite verification; it does not confirm a successful restore test. See [Check Backup Status](#check-backup-status) for upload and restore-test results.

## Check Backup Status

Open **Manage Backups** (`/wp-admin/admin.php?page=ManageBackups`) to check **Last Run**, **Next Run**, destinations, and errors. Hover over **Last run reported errors** or **Last run notes** to read the details. These badges show tooltips; they do not open a copyable log. Use [Export Diagnostics](#export-diagnostics) for a downloadable report.

Starting a task with **Run Now** opens a progress window. Use **View Progress** or **View Result** to inspect the run. Closing the progress window leaves the backup running.

Click **Cancel Backup** in the task's progress window to stop the current run. Completed sites keep their backups, and the task's schedule stays unchanged.

For an on-demand backup, use **View progress** on **Snapshots & Restore** to reopen its progress window or **Cancel backup** to stop the current run.

Use the task's action menu to **Edit**, **Pause**, **Resume**, or **Delete** it. When deleting a task, clear **Also delete this task's snapshots** if you want to keep its backups. This option is selected by default.

A later **Clean Up** for the site deletes these retained snapshots and their cloud copies. See [Retention and Cleanup](#retention-and-cleanup).

On **Snapshots & Restore**, select a site and check **Available from** and the upload details.

If a snapshot shows **files not backed up**, click the warning to inspect the listed paths. A completed backup can still omit files. Resolve any unexpected omissions and create another backup before relying on it.

| Status | Meaning |
| --- | --- |
| Uploading / Waiting to Upload | The copy has not finished reaching its destination |
| Partially Uploaded | Some configured remote copies completed, but others have not |
| Upload Failed / Re-enter Credentials | Inspect the error and test or update the affected storage connection |
| Offsite Verified | All remote uploads for this snapshot completed and passed verification |
| Damaged Archive | A backup archive failed an integrity check. Review the reported error and create a new full backup. |

**Offsite Verified** includes remote file size checks. It does not confirm that the backup can restore the site.

The **Test Restore** column shows automatic restore test results. MainWP periodically tests selected backups in a temporary environment on the Dashboard, leaving the live Child Site unchanged. **Couldn't test here** can indicate missing database permissions on the Dashboard host. Test a restore on a staging site as well.

### Backup Notification Emails

Review **Send email when backup starts** and **Send email when backup fails** under **top-right user menu > MainWP Settings > Backup Settings** (`/wp-admin/admin.php?page=BackupSettings`). Confirm that your Dashboard can send email before relying on these alerts.

Scheduled backup alerts normally go to the WordPress profile email of the account that last saved the task. To change that account's address, sign in as that user and open **WordPress Users > Profile** (`/wp-admin/profile.php`). A previously saved MainWP notification address from an older setup can take precedence. There is no separate recipient list for backup alerts on Backup Settings, and the recipient lists on Email Settings do not control these alerts.

The failure alert covers errors while executing the scheduled backup task. A later failure during a remote upload does not trigger that alert; also check the snapshot's upload status.

### Download a Backup

Click **Download** beside a snapshot when its archive is available on the Dashboard.

Incremental backups cannot be downloaded as one archive. Use **Restore** to restore the selected point in the chain. Backups stored only on remote storage can be restored, but cannot be downloaded through the Dashboard.

## Retention and Cleanup

Each scheduled task has its own **Backup Retention** settings, applied separately to each Child Site. For example, **Keep last** set to seven is a separate count for each site in that task, not a shared total across all selected sites. Another task for the same site has its own policy.

![Backup Retention settings in dark mode, including count, age and storage limits, Remove local archives after upload, and Remove cloud copies too.](/images/sites/built-in-backups/backup-retention.jpg)

| Setting | Effect |
| --- | --- |
| Keep last | Retains the selected number of backups or complete incremental chains |
| Remove backups older than (days) | Makes older backups or chains eligible for removal |
| Storage cap (MB) | Removes older backups or chains when their combined size exceeds the cap |
| Remove local archives after upload | Removes Dashboard archives from new backups after every selected destination has a verified upload; requires at least one remote destination |
| Start a new chain after (backups) | Creates a new full base after an incremental chain reaches this length, including its initial full backup |
| Remove cloud copies too | Also deletes the corresponding remote copies when task retention removes a backup |

When task retention removes a backup, it removes the Dashboard's backup files. Enable **Remove cloud copies too** to include the corresponding remote copies in that cleanup. If it is off, the remote copies remain.

Enable **Remove local archives after upload** to save disk space on the Dashboard after uploads finish. It applies to new backups created by the task, including runs started with **Run Now**, and leaves existing backup archives unchanged. MainWP keeps the file inventories needed for incremental backups. Snapshots whose archives are available only remotely show **Remote only** and can still be restored, but cannot be downloaded through the Dashboard. Normal task retention still applies.

Leave a retention limit blank or enter zero for no limit. Each enabled limit can make older backups eligible for removal. For example, **Keep last** set to seven can remove an older backup before a 30-day age limit is reached. For age-based cleanup alone, leave **Keep last** and **Storage cap (MB)** blank. The age limit is a cleanup threshold, not a guaranteed minimum storage period.

Scheduled retention keeps the newest complete, restorable backup or chain for each task and site, even if it exceeds the storage cap. Incremental chains are kept or removed together, so **Keep last** counts chains rather than individual snapshots.

For **Back Up Now**, set **On-demand backups to keep** under **top-right user menu > MainWP Settings > Backup Settings** (`/wp-admin/admin.php?page=BackupSettings`). The default is five per site, with a minimum of one.

<Note>
**Leftover backup files to keep** in **Backup Settings** controls cleanup of older downloaded files in each site's backup folder on the Dashboard. It applies to files that are not protected by completed snapshots or active runs. The default is one; zero keeps all leftover files. It does not limit completed snapshots or copies at storage destinations.
</Note>

On **Snapshots & Restore**:

- Use **Delete** to remove a backup. Select **Also delete cloud copies** to remove its copies from storage destinations.
- Use **Clean Up** to remove leftover files from interrupted backups, prune on-demand backups beyond the keep count, and delete snapshots whose task was deleted.
- Enable **Show removed backups** to see removal history and reasons.

<Warning>
**Clean Up** also deletes cloud copies of snapshots whose task was deleted, even if you kept those snapshots when deleting the task. Deleted backups can no longer be restored.

Use the Dashboard controls for cleanup. Do not delete individual incremental chain files or the entire Child Site `wp-content/uploads/mainwp` directory. That directory can contain other MainWP data and encryption material.
</Warning>

### Minimum Retention at a Destination

Open **Backups > Storage** (`/wp-admin/admin.php?page=ManageBackupsStorage`) and add or edit a destination. Set **Minimum retention (days)** to the minimum time its copies should remain before automatic cleanup can remove them. Set it to zero to disable this protection.

The period starts when the upload is verified. For older backups without a recorded upload time, MainWP uses the snapshot's creation time. Task count, age, and storage limits do not override this minimum. A protected snapshot can also keep its incremental chain from being removed automatically.

Manual deletion can override the minimum. Review the confirmation before deleting a snapshot or its cloud copies.

## Restore a Backup

You can restore a snapshot to its original Child Site. Connect the site and wait for any running backup or restore to finish before starting.

<Steps>
<Step title="Select the site and snapshot">
Open **Backups > Snapshots & Restore** (`/wp-admin/admin.php?page=ManageBackupsSnapshots`). Select the site, check the snapshot date and type, and click **Restore**.

MainWP can use an available local or completed remote copy. For incremental backups, the required chain must be available.
</Step>

<Step title="Review what will be replaced">
A full or incremental restore replaces files and database content. A database restore changes the database only; a files-only restore leaves the database in place.

Changes made after the snapshot may be lost. Review any warnings before proceeding.
</Step>

<Step title="Keep the safety backup enabled">
Leave **Create a safety backup first** selected. This backup stays on the Child Site and lets you roll back if the restore fails or you need to undo it.

Confirm **I understand this replaces the current site content**, then click **Start Restore**.

![Restore Backup confirmation with the replacement warning, safety backup enabled, consent checkbox, and optional WooCommerce order preservation.](/images/sites/built-in-backups/restore-confirmation.jpg)
</Step>

<Step title="Check the restored site">
Wait for **Restore completed**, then click **Visit site**. Check key pages, sign-in, and other site functions. Review any warnings and the **Recent restores** list.
</Step>
</Steps>

### Cancel or Roll Back a Restore

**Cancel Restore** stops further processing but does not undo files already replaced. If a safety backup is available, use **Roll Back** to return to the site's state before the restore.

If the restore finished on the Child Site but the Dashboard cannot reconnect, click **Stop Checking** to end the connection checks. This marks the restore as failed without rolling it back. Visit the site to check its state.

After a failed database restore, resolve the reported database problem before removing maintenance mode.

<Accordion title="Restoring a WooCommerce store">
Restoring a database normally replaces orders, customers, and other data with the snapshot's version.

When available, select **Preserve orders placed since the backup** to keep live order tables and reapply recent customer and stock data. This requires High-Performance Order Storage (HPOS), order-table synchronization turned off, an HPOS backup, and a matching WooCommerce database version. Older order-table contents from the backup are not restored.

If those conditions are not met, the restore stops with an explanation. Review order, customer, and stock data after any store restore.
</Accordion>

## Require a Backup Before Updates

In **top-right user menu > MainWP Settings > General Settings > Updates Settings** (`/wp-admin/admin.php?page=Settings`), enable **Require a backup before an update** and set **Days without of a full backup tolerance**.

Use this setting to require a recent backup before updating from **Manage Sites**.

Built-in backups accept completed full, database-only, or incremental backups within the allowed age. Files-only backups do not qualify.

Enable **Require an offsite-verified backup** to also require verified copies on remote storage. Local Path destinations do not count as offsite storage. Wait for remote uploads to finish before retrying the update.

For recovery after a failed update, see [Safe Updates & Rollback](/sites/updates/does-mainwp-have-safe-updates).

## Troubleshooting and Limitations

| Symptom | What to check |
| --- | --- |
| Backup screens are missing | Enable built-in backups, check the primary backup system, and confirm your account has the relevant permissions |
| Backup stays on the Dashboard | Check Upload to storage on the task, or read the destination message before Back Up Now |
| Upload fails | Use Test on the destination, check credentials, available space, and access to the configured bucket or directory |
| Scheduled work or background uploads stall | Check Dashboard cron, server loopback requests, and the task error. See [Cron configuration](/customization/manage-wp-cron-on-low-traffic-mainwp-dashboard). |
| Restore is unavailable | Check that the site is connected and the backup files are available. Update MainWP Child and sync again when prompted. |
| Large backup is slow or times out | Check free disk space, use Tar GZip, and review cache and old-backup exclusions |
| File backup is refused because content is outside the WordPress folder | Built-in backups do not support this layout for file backups or restores. Use database-only tasks and your host's file backups. |

Sites with `wp-content` or uploads outside the WordPress core directory, including symlinked folders, cannot use file backups or restores. Create a **Database Backup** task for these sites; **Back Up Now** always creates a full backup.

A database-only restore may also stop on these sites because the safety backup includes files. Keep an independent backup and follow the error message before retrying without the safety backup.

### Export Diagnostics

Export diagnostics from **top-right user menu > MainWP Settings > Backup Settings** (`/wp-admin/admin.php?page=BackupSettings`).

1. Enable **Backup run diagnostics** and click **Save Settings**. The **Export diagnostics data** button appears after saving.
2. If diagnostics was not enabled when the problem occurred, run the affected backup task again to record it. If it was already enabled, you can export the existing data.
3. Click **Export diagnostics data** to download the report to your computer. Attach the downloaded file to your support request with the task name, backup type, storage provider, and time of the failed run.

The report normally downloads as a ZIP. Extract it and open `tasks.json` in a text editor to read the stored task errors under `backup_errors` and notes under `backup_notices`. Detailed run events are in the `events/` folder as `.jsonl` files. If ZIP support is unavailable on the Dashboard, the report downloads as a JSON file instead.

This is a diagnostics package for troubleshooting, not an on-screen log viewer. Detailed run logs are recorded only while diagnostics is enabled and are kept on the Dashboard for up to two weeks.

## API Backups

To create and restore backups through your hosting provider, see [API Backups](/sites/backups/api-backups). Provider setup instructions include:

- [cPanel backups](/sites/backups/api-backups#cpanel-backups)
- [DigitalOcean setup](/sites/backups/api-backups#connect-digitalocean)
- [Kinsta setup and downloads](/sites/backups/api-backups#connect-kinsta)

## Self-Check Checklist

- [ ] Built-in backups are enabled and the test Child Site syncs successfully
- [ ] A first backup completed and appears under Snapshots & Restore
- [ ] The expected storage copies completed, including Offsite Verified when required
- [ ] Scheduled tasks have the intended sites, destinations, exclusions, and retention
- [ ] The recovery passphrase is stored separately if encryption is enabled
- [ ] A restore has been checked on a test site
- [ ] The Dashboard itself has a separate backup
