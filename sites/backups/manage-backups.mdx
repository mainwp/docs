Native Backups lets you back up and restore Child Sites directly from MainWP Dashboard, without a backup add-on or third-party backup plugin.

MainWP Child creates the backup and sends it to your Dashboard. You can also store copies on remote storage or a mounted drive.

<Info>
This guide covers Native Backups in the MainWP 6.4 Release Candidate (RC). Keep MainWP Dashboard and MainWP Child updated, and test backups and restores on a staging site.
</Info>

To manage your hosting provider's backups, use [API Backups](/sites/backups/api-backups). For third-party backup plugins, see [Backup Add-ons](/add-ons/backups).

## What You'll Learn

- Create your first backup and confirm where it is stored
- Schedule full, database, files-only, and incremental backups
- Connect storage destinations and protect backups with encryption
- Restore a site and roll back using a safety backup
- Manage retention and investigate failed jobs

## Prerequisites

- MainWP Dashboard 6.4 running PHP 8.3 or higher
- MainWP Child with Native Backups support, running PHP 7.4 or higher
- A connected Child Site that syncs successfully
- An administrator account to enable and configure backup settings
- Enough free disk space on the Child Site and Dashboard for backup and restore files
- Working WordPress cron on the Dashboard for schedules and background tasks
- Storage credentials if you want copies outside the Dashboard

Keep a separate backup of your MainWP Dashboard installation, including its database and backup encryption keys.

## Find the Backup Screens

Open **MainWP > Sites > Backups** after enabling Native Backups.

| Screen | Use it for | Relative URL |
| --- | --- | --- |
| Top-right user menu > MainWP Settings > General Settings > Backup Settings | Enable Native Backups, encryption, diagnostics, and on-demand retention | `/wp-admin/admin.php?page=Settings` |
| Backups > Manage Backups | View schedules, run tasks, and inspect errors | `/wp-admin/admin.php?page=ManageBackups` |
| Backups > Add New | Create a scheduled backup task | `/wp-admin/admin.php?page=ManageBackupsAddNew` |
| Backups > Storage | Connect and test storage destinations | `/wp-admin/admin.php?page=ManageBackupsStorage` |
| Backups > Snapshots & Restore | Create an on-demand backup, download, restore, or clean up snapshots | `/wp-admin/admin.php?page=ManageBackupsSnapshots` |

A **task** defines what to back up, which sites to include, and when to run. A **snapshot** is a backup of one site at a particular time. One task can create snapshots for several sites.

## Create Your First Backup

<Steps>
<Step title="Enable Native Backups">
Open **top-right user menu > MainWP Settings > General Settings** (`/wp-admin/admin.php?page=Settings`). In **Backup Settings**, turn on **Enable native backups** and save.

If **Select primary backup system** is shown, select **Native backups**.
</Step>

<Step title="Choose where to store the backup">
The backup stays on your Dashboard server unless you add another destination.

For an additional copy, open **Backups > Storage**, add and test a destination, and select **Use as default destination**. See [Configure Storage](#configure-storage).
</Step>

<Step title="Select the site and start the backup">
Open **Backups > Snapshots & Restore** (`/wp-admin/admin.php?page=ManageBackupsSnapshots`) and select your test site.

Read the destination message, then click **Back Up Now**. This creates a full backup. To run a different backup type, create a task and use **Run Now** instead.
</Step>

<Step title="Confirm the result">
Wait for the backup to finish and confirm that a new snapshot appears with the expected date, type, and size.

If you selected remote storage, wait for the upload to finish. See [Check Backup Status](#check-backup-status).
</Step>
</Steps>

<Note>
**Back Up Now** uses the destinations selected on the site's scheduled tasks. If those tasks have no destinations, the backup stays on the Dashboard. The default destination applies only to sites without a scheduled task.
</Note>

## Configure Storage

Completed backups are stored in the Dashboard's private backup directory. Storage destinations receive additional copies. Keep enough free space on both the Dashboard and Child Site to create and process backups.

When moving the Dashboard, [include its private backup directory in the transfer](/advanced/how-to-migrate-the-mainwp-dashboard#preserve-native-backup-files).

<Steps>
<Step title="Add a destination">
Open **Backups > Storage** (`/wp-admin/admin.php?page=ManageBackupsStorage`) and click **Add Destination**. Enter a descriptive **Destination name**, then choose a **Provider**.
</Step>

<Step title="Enter the provider details">
Enter the details listed below for your provider. The account needs permission to upload, read, and delete backup files at that destination.
</Step>

<Step title="Test and save">
Click **Test Connection & Save**. Resolve any connection error before assigning the destination to a backup task.

For Dropbox, use **Connect Dropbox** to approve the connection. A successful connection tests and saves the destination.
</Step>

<Step title="Assign the destination">
On each backup task, select one or more destinations under **Upload to storage**.

Choose **Use as default destination** or **Make default** to preselect a destination for new tasks. Update existing tasks separately if you want them to use it.
</Step>
</Steps>

| Provider | Details to enter |
| --- | --- |
| S3 Compatible Storage | Bucket, Region, Access key, and Secret key. Leave Endpoint empty for Amazon S3; enter your service's endpoint for other S3-compatible storage. Enable Path style addressing when your service requires it. |
| Google Cloud Storage | Bucket, HMAC access key, and HMAC secret from your storage interoperability settings. |
| Dropbox | App key, App secret, and an optional Folder. Register the exact Redirect URI shown in MainWP in your Dropbox app, then use Connect Dropbox. The app needs `files.content.write`, `files.content.read`, and `files.metadata.read` permissions. |
| SFTP | Host, Port, Username, and an existing absolute Directory path. Use a Password or a PEM Private key. When a private key is supplied, Password is its passphrase. |
| Local Path | An absolute Directory path on the Dashboard server, such as a mounted storage directory. It must be writable by the Dashboard. |

For SFTP, you can supply the server's **Host key fingerprint** to verify its identity. If left empty, the first key received is trusted and pinned. Obtain the fingerprint from your server administrator when possible.

**Local Path** does not count as offsite storage, even on a mounted drive, and cannot satisfy **Require an offsite-verified backup**.

### Encrypt Backup Archives

Open **top-right user menu > MainWP Settings > General Settings > Backup Settings** (`/wp-admin/admin.php?page=Settings`):

1. Set a **Backup recovery passphrase**. The first setup also asks for your WordPress password. Store the passphrase separately from the Dashboard.
2. Enable **Encrypt backup archives** and save.

MainWP encrypts new archives before uploading them. Existing snapshots remain unchanged. To change the recovery passphrase, enter the current and new passphrases. Leave the fields blank to keep the existing passphrase.

<Warning>
Keep the recovery passphrase and your Dashboard's encryption keys safe. The passphrase can recover a lost encryption key, but you still need backups of the Dashboard database and backup files.
</Warning>

S3 **Server-side encryption** encrypts the stored copy at the provider. You can use it alongside MainWP's archive encryption.

## Create a Scheduled Backup

Open **Backups > Add New** (`/wp-admin/admin.php?page=ManageBackupsAddNew`).

<Steps>
<Step title="Name the task and select its sites">
Enter a **Backup task name** that describes its purpose, such as "Daily client sites". Select the Child Sites to include.
</Step>

<Step title="Choose the backup type and schedule">
Select a **Backup type** from the table below. Choose **Daily**, **Weekly**, **Monthly**, or **Every N hours**.

Times use the Dashboard WordPress site's timezone. Monthly schedules accept days 1 through 28. Leave the optional time empty to run the task at the next scheduler check after its interval has elapsed.
</Step>

<Step title="Choose storage, exclusions, and retention">
Select destinations under **Upload to storage**, review **Backup Excludes**, and set **Backup Retention**.

Leave storage empty to keep backups only on the Dashboard. Set retention limits to control storage use.
</Step>

<Step title="Save and run a first test">
Click **Schedule Backup**. On **Manage Backups**, click **Run Now** for the task to test its configured type and destinations.

Check the result for each site, then confirm the task's **Next run**.
</Step>
</Steps>

### Choose a Backup Type

| Type | What it contains | Restore behavior |
| --- | --- | --- |
| Full Backup | Site files and database, subject to exclusions | Restores files and database |
| Database Backup | Database content, such as posts, settings, and users | Restores the database without replacing files |
| Files Only Backup | Site files without the database, subject to exclusions | Restores files while keeping the current database, when the Child Site supports files-only restore |
| Incremental Backup | A full first backup, then changed files and a fresh database dump on each later run | Reconstructs the selected point in time using its backup chain |

An incremental **chain** includes the initial full backup and the later incremental backups that depend on it. Keep the chain together so MainWP can restore the selected snapshot.

The first incremental task run is full even when started with **Run Now**. If a Child Site lacks incremental support, MainWP takes full backups and records a note on the task. Keep MainWP Child updated and sync the site after updating.

### Archive Format and Exclusions

**Archive type** can use the site setting, the global setting, or an explicit format. The available formats are Zip, Tar, Tar GZip, and Tar BZip2.

For large sites, use **Tar GZip**. MainWP can switch large Zip backups to Tar GZip unless **Keep Zip even when the site is large** is enabled.

Review the exclusion switches for known backup locations, known cache locations, non-WordPress folders, and ZIP archives. Excluding old backup archives avoids repeatedly backing up earlier backups. Do not exclude files you expect to recover.

Enter **Custom excludes** as paths relative to the Child Site's WordPress directory, separated by newlines or commas. For example, `wp-content/cache`.

## Check Backup Health

View **Backup Health** in **MainWP > Sites > Manage Sites** (`/wp-admin/admin.php?page=managesites`) or **MainWP > Operations** (`/wp-admin/admin.php?page=mainwp_tab`). The summary appears when Native Backups is enabled and your account has permission to run backups.

Each site is classified using its latest completed native snapshot:

| Status | Meaning |
| --- | --- |
| Protected | The snapshot is no more than 24 hours old and its offsite copies are verified. |
| At Risk | The snapshot is over 24 hours old but no more than 7 days old, or is no more than 24 hours old without verified offsite copies. |
| Critical | The latest completed snapshot is more than 7 days old. |
| No Backup | No completed native snapshot is recorded. |

Click a status to filter Manage Sites to the matching sites. For **At Risk**, check the backup schedule and storage uploads. For **Critical** or **No Backup**, run a backup and confirm it completes.

A recent backup stored only locally shows **At Risk**. **Protected** confirms backup age and offsite verification; it does not confirm a successful restore test. See [Check Backup Status](#check-backup-status) for upload and restore-test results.

## Check Backup Status

Open **Manage Backups** (`/wp-admin/admin.php?page=ManageBackups`) to check **Last run**, **Next run**, destinations, and errors. Click **Last run reported errors** or **Last run notes** to review the details.

Use the task's action menu to **Edit**, **Pause**, **Resume**, or **Delete** it. When deleting a task, clear **Also delete this task's snapshots** if you want to keep its backups. This option is selected by default.

For email notifications, review **Send email when backup starts** and **Send email when backup fails** under **top-right user menu > MainWP Settings > General Settings > Backup Settings** (`/wp-admin/admin.php?page=Settings`). Confirm that your Dashboard can send email before relying on these alerts.

On **Snapshots & Restore**, select a site and check **Available from** and the upload details.

| Status | Meaning |
| --- | --- |
| Uploading / Waiting to upload | The copy has not finished reaching its destination |
| Partially uploaded | Some configured remote copies completed, but others have not |
| Upload failed / Re-enter credentials | Inspect the error and test or update the affected storage connection |
| Offsite Verified | All remote uploads for this snapshot completed and passed verification |

**Offsite Verified** includes remote file size checks. It does not confirm that the backup can restore the site.

The **Test Restore** column shows automatic restore test results. MainWP periodically tests selected backups in a temporary environment on the Dashboard, leaving the live Child Site unchanged. **Couldn't test here** can indicate missing database permissions on the Dashboard host. Test a restore on a staging site as well.

### Download a Backup

Click **Download** beside a snapshot when its archive is available on the Dashboard.

Incremental backups cannot be downloaded as one archive. Use **Restore** to restore the selected point in the chain. Backups stored only on remote storage can be restored, but cannot be downloaded through the Dashboard.

## Retention and Cleanup

Each scheduled task has its own retention settings, applied per site.

| Setting | Effect |
| --- | --- |
| Keep last | Retains the selected number of backups or complete incremental chains |
| Remove backups older than (days) | Makes older backups or chains eligible for removal |
| Storage cap (MB) | Removes older backups or chains when their combined size exceeds the cap |
| Start a new chain after (backups) | Creates a new full base after an incremental chain reaches this length, including its initial full backup |
| Remove cloud copies too | Also removes the corresponding copies from the task's storage destinations |

Leave a retention limit blank or enter zero for no limit. MainWP always keeps the newest complete, restorable backup or chain, even if it exceeds the storage cap. Incremental chains are kept or removed together, so **Keep last** counts chains rather than individual snapshots.

For **Back Up Now**, set **On-demand backups to keep** under **top-right user menu > MainWP Settings > General Settings > Backup Settings** (`/wp-admin/admin.php?page=Settings`). The default is five per site, with a minimum of one.

On **Snapshots & Restore**:

- Use **Delete** to remove a backup. Select **Also delete cloud copies** to remove its copies from storage destinations.
- Use **Clean Up** to remove leftover folders and old backups that meet the retention rules.
- Enable **Show removed backups** to see removal history and reasons.

<Warning>
Use the Dashboard controls for cleanup. Do not delete individual incremental chain files or the entire Child Site `wp-content/uploads/mainwp` directory. That directory can contain other MainWP data and encryption material.
</Warning>

## Restore a Backup

You can restore a snapshot to its original Child Site. Connect the site and wait for any running backup or restore to finish before starting.

<Steps>
<Step title="Select the site and snapshot">
Open **Backups > Snapshots & Restore** (`/wp-admin/admin.php?page=ManageBackupsSnapshots`). Select the site, check the snapshot date and type, and click **Restore**.

MainWP can use an available local or completed remote copy. For incremental backups, the required chain must be available.
</Step>

<Step title="Review what will be replaced">
A full or incremental restore replaces files and database content. A database restore changes the database only; a files-only restore leaves the database in place.

Changes made after the snapshot may be lost. Review any warnings before proceeding.
</Step>

<Step title="Keep the safety backup enabled">
Leave **Create a safety backup first** selected. This backup stays on the Child Site and lets you roll back if the restore fails or you need to undo it.

Confirm **I understand this replaces the current site content**, then click **Start Restore**.
</Step>

<Step title="Check the restored site">
Wait for **Restore completed**, then click **Visit site**. Check key pages, sign-in, and other site functions. Review any warnings and the **Recent restores** list.
</Step>
</Steps>

### Cancel or Roll Back a Restore

**Cancel Restore** stops further processing but does not undo files already replaced. If a safety backup is available, use **Roll Back** to return to the site's state before the restore.

If the restore finished on the Child Site but the Dashboard cannot reconnect, click **Stop Checking** to end the connection checks. This marks the restore as failed without rolling it back. Visit the site to check its state.

After a failed database restore, resolve the reported database problem before removing maintenance mode.

<Accordion title="Restoring a WooCommerce store">
Restoring a database normally replaces orders, customers, and other data with the snapshot's version.

When available, select **Preserve orders placed since the backup** to keep live order tables and reapply recent customer and stock data. This requires High-Performance Order Storage (HPOS), order-table synchronization turned off, an HPOS backup, and a matching WooCommerce database version. Older order-table contents from the backup are not restored.

If those conditions are not met, the restore stops with an explanation. Review order, customer, and stock data after any store restore.
</Accordion>

## Require a Backup Before Updates

In **top-right user menu > MainWP Settings > General Settings > Updates Settings** (`/wp-admin/admin.php?page=Settings`), enable **Require a backup before an update** and set **Days without of a full backup tolerance**.

Use this setting to require a recent backup before updating from **Manage Sites**.

Native Backups accepts completed full, database-only, or incremental backups within the allowed age. Files-only backups do not qualify.

Enable **Require an offsite-verified backup** to also require verified copies on remote storage. Local Path destinations do not count as offsite storage. Wait for remote uploads to finish before retrying the update.

For recovery after a failed update, see [Safe Updates & Rollback](/sites/updates/does-mainwp-have-safe-updates).

## Troubleshooting and Limitations

| Symptom | What to check |
| --- | --- |
| Native Backup screens are missing | Enable Native Backups, check the primary backup system, and confirm your account has the relevant permissions |
| Backup stays on the Dashboard | Check Upload to storage on the task, or read the destination message before Back Up Now |
| Upload fails | Use Test on the destination, check credentials, available space, and access to the configured bucket or directory |
| Scheduled work or background uploads stall | Check Dashboard cron, server loopback requests, and the task error. See [Cron configuration](/customization/manage-wp-cron-on-low-traffic-mainwp-dashboard). |
| Restore is unavailable | Check that the site is connected and the backup files are available. Update MainWP Child and sync again when prompted. |
| Large backup is slow or times out | Check free disk space, use Tar GZip, and review cache and old-backup exclusions |
| File backup is refused because content is outside the WordPress folder | Native Backups does not support this layout for file backups or restores. Use database-only tasks and your host's file backups. |

Sites with `wp-content` or uploads outside the WordPress core directory, including symlinked folders, cannot use file backups or restores. Create a **Database Backup** task for these sites; **Back Up Now** always creates a full backup.

A database-only restore may also stop on these sites because the safety backup includes files. Keep an independent backup and follow the error message before retrying without the safety backup.

### Export Diagnostics

Enable **Backup run diagnostics** under **top-right user menu > MainWP Settings > General Settings > Backup Settings** (`/wp-admin/admin.php?page=Settings`), save, and reproduce the problem.

Click **Export diagnostics data** and include the export in your support request, along with the task, backup type, storage provider, and exact error. Diagnostics are stored on the Dashboard for two weeks.
