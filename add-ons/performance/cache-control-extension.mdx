MainWP Cache Control can automatically purge cache after MainWP Dashboard updates WordPress core, themes, or plugins on your MainWP Child sites. You can also manually purge cache for one site, selected sites, or all connected sites.

## Prerequisites

- Activate and configure a supported caching plugin or service on each MainWP Child site you want to purge, or configure Cloudflare purging for that site. Cache Control sends purge requests to the existing cache; it does not set up the caching solution.
- For **WP-Optimize**, enable **page caching** in the plugin's settings. Activating the plugin alone is not enough for Cache Control to detect it.
- Sync the sites after configuring their caching solution so MainWP Dashboard receives the detected cache information.

## Supported Cache Systems

Cache Control supports Cloudflare and the following cache plugins or cache services:

- AccelerateWP
- Autoptimize
- Breeze
- Cache Enabler
- Comet Cache
- FastPixel Cache
- FlyingPress
- Hummingbird Performance
- LiteSpeed Cache
- Nginx Helper
- Nitropack
- Pressable Cache Management
- Rocket.net CDN Cache Plugin
- RunCloud Hub
- Seraphinite Accelerator
- SiteGround Optimizer
- Swift Performance
- Swift Performance Lite
- Swis Performance
- W3 Total Cache
- WP Fastest Cache
- WP Optimize
- WP Rocket
- WP Super Cache

If a MainWP Child site has both Cloudflare and a supported cache plugin enabled, Cache Control can purge both during the same operation. When the Rocket.net CDN Cache Plugin is detected, Cloudflare purging is skipped to avoid double-purging the same Cloudflare-backed cache layer.

### Cloudflare API Token Permissions

For **API Token** authentication, [create a Cloudflare API token](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) with both of these zone permissions:

- **Zone - Read**, which allows MainWP Child to [find the site's zone](https://developers.cloudflare.com/api/resources/zones/methods/list/).
- **Cache Purge**, which allows MainWP Child to [purge the zone's cache](https://developers.cloudflare.com/api/resources/cache/methods/purge/).

Scope the token to the zones you want to manage. A token saved in the global settings must cover the zones of all sites using that configuration. The same permission requirements apply to site-specific tokens.

## Configure Global Settings

Use the global settings when most of your MainWP Child sites should use the same cache behavior.

<Steps>
  <Step title="Open Cache Control">
    In MainWP Dashboard, go to **MainWP > Add-ons > Cache Control**.
  </Step>
  <Step title="Enable automatic cache purging">
    Turn on **Automatically purge cache** to purge supported cache after MainWP Dashboard updates WordPress core, themes, or plugins.
  </Step>
  <Step title="Optional: enable Cloudflare cache purging">
    Turn on **Purge Cloudflare cache** if you want Cache Control to purge Cloudflare cache for sites that use the global Cloudflare account.
  </Step>
  <Step title="Set the maximum concurrent requests">
    For **Maximum concurrent requests**, choose how many cache purge requests Cache Control sends at the same time during a bulk purge, from **1** to **10**. The default is **3**.
  </Step>
  <Step title="Set the delay between requests">
    For **Delay between requests**, choose how many seconds Cache Control waits before starting the next purge request during a bulk purge, from **0 seconds** to **10 seconds**. The default is **0 seconds**.
  </Step>
  <Step title="Optional: enter Cloudflare credentials">
    If you enabled **Purge Cloudflare cache**, the **Cloudflare API Credentials** section appears. Select **Email & API key** or **API Token**, then enter the matching Cloudflare credentials. For a token, use the [permissions described above](#cloudflare-api-token-permissions).
  </Step>
  <Step title="Save and sync">
    Click **Save Settings**, then sync your MainWP Dashboard with your MainWP Child sites so the new settings are sent to the sites.
  </Step>
</Steps>

![Cache Control global settings with Automatically purge cache and Purge Cloudflare cache toggles](/images/add-ons/cache-control-global-settings.png)

<Note>
When **Purge Cloudflare cache** is enabled and the required credential fields are filled in, Cache Control checks the credentials after you click **Save Settings**. If Cloudflare returns an error, the settings are saved, but MainWP Dashboard shows a warning with the Cloudflare API error so you can correct the credentials before syncing.

This checks credential validity, not permission to find or purge a particular site's zone. Empty credentials are not validated. After saving and syncing, run a manual purge and review its result to check the site's Cloudflare setup.
</Note>

## Configure a Single Site

Use single-site settings when one MainWP Child site needs different cache behavior or different Cloudflare credentials from the global settings.

<Steps>
  <Step title="Open the site">
    In MainWP Dashboard, go to **MainWP > Sites > Manage Sites**, locate the site, and open its site dashboard.
  </Step>
  <Step title="Open Cache Control">
    Go to the site's **Cache Control** page.
  </Step>
  <Step title="Set automatic purging">
    For **Automatically purge cache**, choose **Yes**, **No**, or **Use global setting**.
  </Step>
  <Step title="Set Cloudflare behavior">
    For **Purge Cloudflare cache**, choose **Use global setting**, **Yes (use site-specific credentials)**, or **No (disabled for this site)**.
  </Step>
  <Step title="Optional: enter site-specific Cloudflare credentials">
    If you choose **Yes (use site-specific credentials)**, select **Email & API key** or **API Token**, then enter the Cloudflare credentials for that site. Site-specific tokens need the [same zone permissions](#cloudflare-api-token-permissions).
  </Step>
  <Step title="Save and sync">
    Click **Save Settings**, then sync the MainWP Child site.
  </Step>
</Steps>

<Note>
Site-specific Cloudflare credentials are checked on save when **Yes (use site-specific credentials)** is selected and the required fields are filled in. If Cloudflare returns an error, MainWP Dashboard shows the returned API error in a warning notice. As with global credentials, this check does not test a purge of the site's zone.
</Note>

## Manually Purge Cache

Cache Control can purge cache automatically after updates, but you can also start a manual purge from MainWP Dashboard.

Bulk purges follow the **Maximum concurrent requests** and **Delay between requests** values from the global settings. Lower the concurrent requests or add a delay if bulk purges overload your server or trigger rate limits on your hosting or Cloudflare account. Raise the concurrent requests to finish bulk purges faster across many sites.

### From Manage Sites

Go to **MainWP > Sites > Manage Sites**, select the sites, choose **Purge Cache (Cache Control)** from the bulk actions menu, and click **Apply**.

![Animated screenshot showing the Purge Cache Cache Control bulk action on the Manage Sites page](/images/add-ons/cache-control-manage-sites-purge.gif)

If a selected site does not have a supported cache plugin detected and does not have Cloudflare purging enabled, MainWP Dashboard shows a warning for that site instead of reporting a successful purge.

### From Widgets

The **Updates Overview** widget includes **Clear Cache** on the **Operations** page and an individual site's **Overview** page. Use it on Operations to purge all connected sites, or on an individual site's Overview to purge only that site. If the widget is hidden, enable **Updates Overview** from **Page Settings** for that screen.

![Updates Overview widget showing the Clear Cache button and View Cache Control Logs button](/images/add-ons/cache-control-widget-purge.png)

## View Cache Control Status

The **MainWP > Sites > Manage Sites** table can show Cache Control columns such as **Last Purged Cache** and **Cache Solution**. These columns help you confirm when cache was last purged and which supported cache plugin MainWP Child detected on each site.

## View Logs

After a manual purge finishes, sync the affected MainWP Child sites to refresh the purge information stored in MainWP Dashboard. Then go to **MainWP > Add-ons > Cache Control > Logs** to review the log table. Reloading Logs without syncing can leave the previous purge result and timestamp displayed.

The log table includes:

- **Site** - The MainWP Child site name and URL.
- **Status** - Whether automatic cache purging is enabled for that site after global and site-specific settings are applied.
- **Cache Solution** - The detected cache plugin or a not-found value when no supported cache plugin is detected.
- **Cloudflare** - A Cloudflare icon that reflects the current Cloudflare purge state.
- **Last Purged** - The most recent plugin or Cloudflare purge time, shown as elapsed time when available.
- **Log** - The plugin and Cloudflare purge messages returned by the site.

The **Cloudflare** column uses three status colors:

| Color | Meaning |
| --- | --- |
| Green | Cloudflare cache purging is enabled with no recorded error. This can also appear before the first purge result is recorded. |
| Yellow | Cloudflare cache purging is enabled, but the latest Cloudflare result returned an error. Check the **Log** column for details. |
| Grey | Cloudflare cache purging is disabled for the site. |

Use **Last Purged** and the **Log** messages to review a purge operation. A green Cloudflare icon alone does not confirm that a purge has run successfully.

## Manage Cache Control from the Abilities API

Cache Control 5.3 registers a `mainwp-cache-control` category with the WordPress [Abilities API](/api-reference/abilities-api/overview). AI agents, the [MainWP MCP Server](/mcp-server/overview), and other automation tools can then read Cache Control status and change policy without visiting the Dashboard UI. Each ability follows the same authentication, transport, and error rules as MainWP's built-in abilities.

Cache Control registers eight abilities in the `mainwp` namespace:

| Ability | Type | Purpose |
| --- | --- | --- |
| `mainwp/get-site-cache-control-status-v1` | Read | Return Dashboard policy and the last cached Child observation (detected cache solution, last reported purge) for one site. |
| `mainwp/list-site-cache-control-statuses-v1` | Read | Paginate the same status payload across sites the caller can see. |
| `mainwp/get-global-cache-control-configuration-v1` | Read | Return the non-secret global policy and a Cloudflare credential readiness classification. |
| `mainwp/set-global-cache-control-policy-v1` | Write | Set the global auto-purge and Cloudflare enablement flags. Does not change credentials or sync sites. |
| `mainwp/set-site-cache-control-policy-v1` | Write | Set one site's auto-purge and Cloudflare source modes. Does not change credentials or sync the Child. |
| `mainwp/validate-cloudflare-credentials-v1` | Read | Validate the effective stored Cloudflare credentials for one site and return a bounded classification. |
| `mainwp/purge-site-cache-v1` | Write (destructive) | Request a cache purge on one Child and return per-layer confirmation. |
| `mainwp/get-site-cache-purge-outcome-v1` | Read | Return the last structured purge outcome cached from one Child. |

Read abilities never contact the Child site or the cache provider. They report what the Dashboard has stored, so a `get` result reflects the last sync rather than live provider state.

### Prerequisites

- WordPress 6.9 or later on the MainWP Dashboard site, so the Abilities API is available.
- MainWP Dashboard 6.0 or later with an API key that carries the `mainwp-cache-control-extension` extension capability and the Dashboard capability required by each ability.
- Cache Control 5.3 or later installed and activated on the Dashboard.

If the Abilities API is not available on the Dashboard, Cache Control skips registration and the endpoints below return `rest_ability_not_found`.

### Discover the abilities

List the Cache Control category through the standard Abilities API discovery endpoint:

```bash
curl -u "admin:APPLICATION_PASSWORD" \
  "https://your-dashboard.com/wp-json/wp-abilities/v1/abilities?category=mainwp-cache-control"
```

Each entry includes the full input and output schemas, plus the `readonly`, `destructive`, and `idempotent` annotations that decide the HTTP method. For the transport rules and full error reference, see the [Abilities API Overview](/api-reference/abilities-api/overview).

### Read one site's status

`mainwp/get-site-cache-control-status-v1` is read-only, so it is called with GET and `input_json`:

```bash
curl -G -u "admin:APPLICATION_PASSWORD" \
  --data-urlencode 'input_json={"site_id":42}' \
  "https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/get-site-cache-control-status-v1/run"
```

The response separates the current Dashboard configuration from the last Child observation:

```json
{
  "site_id": 42,
  "live": false,
  "current_configuration": {
    "source": "dashboard_current_configuration",
    "auto_purge_mode": 2,
    "configured_auto_purge_enabled": true,
    "cloudflare_mode": 0,
    "configured_cloudflare_enabled": true,
    "child_application_status": "unknown"
  },
  "cached_child_observation": {
    "source": "dashboard_cached_child_observation",
    "cache_solution": "WP Rocket",
    "last_reported_purge_at": 1758556800
  }
}
```

`auto_purge_mode` uses `0` disabled, `1` enabled, `2` inherit global. `cloudflare_mode` uses `0` use global, `1` site-specific configuration, `2` disabled. Sync the Child site to refresh `cached_child_observation`.

### Change the global policy

`mainwp/set-global-cache-control-policy-v1` is a write ability, so it is called with POST:

```bash
curl -X POST -u "admin:APPLICATION_PASSWORD" \
  -H "Content-Type: application/json" \
  -d '{"input":{"auto_purge_enabled":true,"cloudflare_enabled":false}}' \
  "https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/set-global-cache-control-policy-v1/run"
```

The response includes both the previous and current values, a `changed` flag, and `sync_status: "not_requested"` to make clear that Child sites are not resynced by this call.

### Purge one site

`mainwp/purge-site-cache-v1` is destructive and non-idempotent, so it is called with POST:

```bash
curl -X POST -u "admin:APPLICATION_PASSWORD" \
  -H "Content-Type: application/json" \
  -d '{"input":{"site_id":42}}' \
  "https://your-dashboard.com/wp-json/wp-abilities/v1/abilities/mainwp/purge-site-cache-v1/run"
```

Follow up with `mainwp/get-site-cache-purge-outcome-v1` to read the last structured purge outcome cached from that Child.

### Use with the MainWP MCP Server

When the MCP server is connected to a Dashboard running Cache Control 5.3, these abilities appear as MCP tools with the primary-namespace naming rules, for example `get_site_cache_control_status_v1` and `purge_site_cache_v1`. Confirmation gating from the [safety model](/mcp-server/safety) applies to `set-*` and `purge-*` because they are not read-only.
