## What You'll Learn

- What the Agent Bridge add-on does

- Who approves agent requests, and when a request waits
- Allow rules, Block rules, and task approvals
- Giving staff members access with Team Control, and letting them run some changes without approval
- Connecting Claude Desktop or Claude Code
- Where agent work is recorded

---

The Agent Bridge add-on lets an AI app, such as Claude or Codex, connected through the [MainWP MCP server](/mcp-server/overview), read and change your child sites through MainWP. You choose what the AI can do on each site, and you can require an administrator to approve requests before they run.

Agent Bridge is built for live sites. By default, an administrator approves their own changes in their AI app, and a staff member's change waits for an administrator unless their Team Control role lets it run without approval. On sites with a backup system, Agent Bridge checks for a recent backup first.

## Requirements

- WordPress 6.9 or later on the Dashboard site. On an older version, the add-on loads nothing and shows "Agent Bridge needs WordPress 6.9 or later" in the WordPress admin.
- PHP 8.3 or later.
- A MainWP Dashboard version that supports Agent Bridge. On an older Dashboard, the add-on shows "This version of MainWP Dashboard doesn't support Agent Bridge. Update MainWP Dashboard to use it."
- WordPress 6.9 or later on each child site where the AI uses site abilities. On an older child site, those requests return "Site abilities require WordPress 6.9 or later on the child site."

## Agent access per site

Agent access is set per site. In your MainWP Dashboard, go to **Sites**, edit a site, and find the **Agent access** setting. Only administrators can change it.

| Level | What the AI can do |
|---|---|
| **Off** | Check the site's status only. This is the default. |
| **Read only** | Read site abilities, run allowlisted read-only WP-CLI commands, and read files. It can't make changes or read `wp-config.php`. |
| **Abilities** | Everything in **Read only**, plus site abilities that make changes. |
| **Abilities and code** | Everything in **Abilities**, plus PHP, WP-CLI commands, and file changes. |

The setting is saved on the child site, so the site needs a current MainWP Child plugin. If it doesn't have one, MainWP shows "Update MainWP Child to use agent tools on this site."

## Site abilities and code tools

The AI works through two kinds of tools:

- **Site abilities** are actions that plugins on the child site register, such as listing or updating WooCommerce products. Each ability says whether it only reads, changes data, or can delete data or be hard to undo. The AI runs it with the matching tool: the read tool, the write tool, or the destructive tool.
- **Code tools** run PHP, run WP-CLI commands, and read or change files on the site.

The abilities label themselves. MainWP trusts the plugin that registered an ability to describe it correctly.

An ability that can delete data or is hard to undo runs only through the destructive tool. If the AI sends it to the read or write tool, the request is refused with a 403 error and this message: "This ability can delete data or is hard to undo. Use the destructive tool, which needs that right." An ability that changes data sent to the read tool is refused the same way, with a message naming the tool to use.

## Who approves requests

Only administrators approve or deny agent requests. An administrator is a user with the WordPress administrator role. A custom role that can manage options but isn't the administrator role counts as staff.

Requests that need approval appear on the **Agent approvals** page in the MainWP menu, on the **Waiting for approval** tab. Each card shows who asked, the site, when the request expires, the exact code or operation, and what happens with the safety backup. Staff members see their own requests with "Waiting for an administrator to approve this in MainWP". They can't approve them, even their own.

After an administrator approves a request, the change runs when the AI continues. Tell the AI to continue once you've approved.

An administrator can approve several requests at once with **Approve selected**. Requests that use the destructive tool have to be approved one at a time on their own cards.

A request waits for 15 minutes. If nobody approves it in that time, it expires and the AI has to ask again. The **Recently decided** tab lists approvals and denials from the last 7 days.

### Approval Mode: Never ask or Ask

The approval **Mode** setting on the **Rules** tab decides when an administrator's change waits for approval. Mode applies to administrators only.

| Mode | What happens |
|---|---|
| **Never ask** (the default) | Administrators approve changes in their AI app. Their confirmation there counts as approval, and nothing waits on the **Agent approvals** page except where an Ask rule or a [store rule](#woocommerce-stores) applies. This includes destructive abilities. The MainWP AI Assistant in your Dashboard has no separate permission prompt, so in saved conversations it keeps showing its **Proceed** card, unless an Allow rule or a task approval covers the request, until an administrator clicks **Save Mode and backup setting** under **Mode and rules** with **Never ask** selected. That button also saves the no-backup setting, so saving only that setting saves the Mode shown too. |
| **Ask** | An administrator's change waits on the **Agent approvals** page unless an Allow rule covers it. |

**Never ask** is the default until you save a Mode. The Rules tab shows **Never ask (default, not saved)** until then.

A staff member's change waits for an administrator in both modes, unless their Team Control role lets them run it without approval. See [Run without approval](#run-without-approval).

Requests that only read never wait.

<Warning>
In **Never ask** mode, the prompt in your AI app is the only check before a change runs, apart from the [store rules](#woocommerce-stores). Content on a child site, such as a post or a plugin's output, can contain text that tries to steer the AI. If you choose your AI app's option to stop asking (in Claude Code: "Yes, and don't ask again") for the PHP, WP-CLI, or file tools, that content can make the AI run code on your sites with no approval in MainWP. Keep the AI app asking for these tools, or set **Mode** to **Ask**.
</Warning>

### Allow rules

An approval card for an administrator's request has an **Always allow** button next to **Approve** and **Deny**. It approves the request and saves an Allow rule for that site that covers all administrators, so the same kind of request doesn't wait again.

- On a site ability request, the rule covers only that ability. For a destructive ability, that includes deletes.
- On a PHP, WP-CLI, or file request, the rule covers the whole tool on that site, not only the request on the card. An Allow rule for PHP lets the AI run any PHP on that site without asking, except on a WooCommerce store.

A staff member's request has no **Always allow** button. When one of the role's run-without-approval options would cover the request, the card links to the staff member's role in Team Control and names that option.

### Block rules and other rules

On the **Rules** tab, under **Add a rule**, an administrator can add a rule for one tool. Pick the scope (all sites, one site, a client, or a tag) and the setting (**Ask**, **Allow**, or **Block**). A Block rule can also name staff users or roles. You can narrow a WP-CLI rule to a command pattern, such as `plugin update *`, and a site ability rule to an ability name or namespace, such as `woocommerce/*`.

- **Block** always applies, in both modes. The AI's requests to use a blocked tool are refused.
- **Ask** and **Allow** apply to changes. Reads don't wait.
- Allow and Ask rules cover administrators. A Block rule that names staff users or roles covers only those staff, and one that names no one covers administrators. To block something for your own AI, save the rule without naming anyone.
- When several rules match, a Block rule wins. Otherwise the most specific rule wins: a site rule over a client rule, a client rule over a tag rule, and a tag rule over an all-sites rule.

To stop an approved request before it runs, turn Agent access off for that site or add a Block rule.

### WooCommerce stores

On a site where WooCommerce is active, or whose plugin list MainWP can't read, PHP, WP-CLI, and file changes or restores always wait for an administrator's approval. Mode, Allow rules, and task approvals don't change this, and these cards have no **Always allow** button. Abilities with the word refund in their name, and WooCommerce's order status abilities when they set an order to Refunded, are refused: refunds and payments are done by a person in WooCommerce. Changing an order's status, adding an order note the customer sees, deleting a customer, and WooCommerce abilities whose names include the word email, checkout, payment, tax, shipping, settings, password, capture, or subscription also always wait. These ability rules apply to changes only, so abilities that only read still run. MainWP matches all of them by name and doesn't check what an ability does, so a refund ability with another name, or another WooCommerce ability that emails a customer, follows your Mode and rules.

### Task approvals

A task approval lets the AI make its other changes on one site without asking each time. It lasts until the AI has been idle for 30 minutes, and 4 hours at most. Task approvals never cover destructive abilities or changes a store rule holds.

Task approvals come from two places:

- **Proceed** on a PHP, WP-CLI, or file card in the MainWP AI Assistant, in a saved conversation, unless a store rule holds the request. The card says "Proceeding also lets this AI make its other changes on this site until it's idle for 30 minutes (4 hours at most)." **Proceed** on a site ability card approves only that ability.
- The **Approve for this task** checkbox on the browser approval page for a [remote AI connection](/mcp-server/remote/approval-policies).

Active task approvals are listed under **Active task approvals** on the **Waiting for approval** tab. Click **End** to stop one early.

### Safety backups

Before a change runs on a site with a backup system, MainWP uses a backup from the last 24 hours or makes a new safety backup. If that backup fails, the change doesn't run and the AI has to ask again after you fix backups for that site in **Settings > Backup Settings**. If MainWP says the private backup directory isn't confirmed, confirm it there first. Under a task approval, asking again gets the same failed backup: an administrator approves the request again or ends the task approval. The **Recently decided** tab shows **Backup failed** for an approved request whose backup failed, and for a change that needed no approval but whose backup failed. Nothing changed in either case.

MainWP counts a site as having a backup system when MainWP's own backups are turned on, or when a backup was recorded for the site in the last 24 hours. MainWP can't start a backup in another backup plugin, so a site that relies on one, with no backup in the last 24 hours, counts as having no backup system.

For sites with no backup system, the **When a site has no backup system** setting on the **Rules** tab decides what happens: **Let the AI make changes** (the default) or **Block AI changes on that site**. The approval card says when a site has no backup system. You can't skip the safety backup for a single request: a site with a backup system always has a recent backup first.

## Staff members and Team Control

A staff member is anyone who isn't a WordPress administrator. Staff members need [Team Control](/add-ons/agency/team-control-extension) permissions to use the Agent Bridge tools. Team Control adds four rights under **Agent Bridge**:

| Right | Tools it allows |
|---|---|
| **Run site abilities (read)** | Listing, looking up, and running site abilities that only read |
| **Run site abilities (write)** | Running site abilities that change data |
| **Run site abilities (destructive)** | Running site abilities that can delete data or are hard to undo |
| **Run code on child sites (PHP, WP-CLI, files)** | The PHP, WP-CLI, and file tools, including the read-only ones |

The site status tool is available to a staff member with any one of these Agent Bridge rights. It also supplies the editing guides needed by site abilities.

A staff member also needs the **Access WP Admin** permission and access to the site through their Team Control role. Without the matching right, the refusal names the right to ask an administrator for. If the right is present but other role access is missing, the request is refused with "Your role can't use agent tools on child sites. Ask an administrator to check your role in Team Control." A site outside the role's access is refused as not found.

Staff members can use the Agent Bridge tools only through the MainWP MCP server with their own Application Password. The MainWP AI Assistant and remote AI connections are available to administrators only.

### Run without approval

Two more options under **Agent Bridge** in the Team Control role editor let the role's staff run some site abilities without waiting for an administrator:

| Option | Abilities it covers |
|---|---|
| **Run without approval: Elementor page and media edits** | `elementor/create-page`, `elementor/build-composition`, `elementor/manage-elements`, `elementor/upload-media`, `elementor/request-media-upload`, `elementor/create-preview-link` |
| **Run without approval: WPForms form and field edits** | `wpforms/create-form`, `wpforms/add-field`, `wpforms/update-field` |

Each option covers only the abilities listed. `wpforms/update-form-settings` isn't included because it sets who receives form submission emails, so it still waits for an administrator. A new Team Control role starts without either option.

These options don't grant access on their own. An option counts only on sites where the same role also has **Run site abilities (write)** and access to the site. If a staff member has more than one role, another role's rights or sites don't extend it. Block rules and the site's Agent access level still apply, and the safety backup still runs first. A Block rule that names no one covers administrators only, so to stop a staff member from running these abilities, name them or their role in the Block rule.

Some changes always wait for an administrator when a staff member asks, whatever the role's options:

- Any site ability not listed above, including Elementor's publish, page settings, and revision abilities
- Site abilities that can delete data or are hard to undo
- PHP, WP-CLI, and file changes or restores

MainWP reads the role's options each time the AI asks or continues. If you remove an option while a request is waiting for its safety backup, that request goes back to waiting for an administrator.

On the **Activity** tab and in Network Activity, a change that ran this way says which role and option allowed it, for example "Ran without approval: Editor role, Elementor page and media edits". If the change was sent but didn't succeed, the line starts "Sent without approval". In Network Activity the line follows the result, starting in lower case.

### When rights change after approval

MainWP checks the requester's access again when an approved request runs. If the requester lost the right, or lost access to the site, after the request was approved, it doesn't run and the AI gets a 403 error. Their task approvals for that site can't be used either.

## Use Agent Bridge from Claude Desktop or Claude Code

Agent Bridge works with any AI app connected through the MainWP MCP server. To connect Claude Desktop or Claude Code with an [Application Password](/mcp-server/quickstart#before-you-start), follow the setup guide for your app:

- [Install in Claude Desktop](/mcp-server/claude-desktop-bundle), or the manual Claude Desktop configuration in [Connect Your AI App](/mcp-server/clients)
- [Install in Claude Code CLI](/mcp-server/claude-code-plugin#install-in-claude-code-cli), or the manual `claude mcp add` command in [Connect Your AI App](/mcp-server/clients)

<Warning>
With **Mode** on **Never ask**, the default, the prompt in the AI app is the only check before an administrator's change runs, apart from the [store rules](#woocommerce-stores). When the app asks to use the PHP, WP-CLI, or file tools, don't choose its option to stop asking (in Claude Code: "Yes, and don't ask again"). Content on a child site can try to steer the AI into running code you didn't ask for. Approve each use in the app, or set **Mode** to **Ask** on the **Rules** tab.
</Warning>

Give each person their own Application Password and name it after the app and computer it's used on, such as "Claude Code on office laptop". The name appears in Network Activity and in the **Key** filter, so you can see everything one key did before you revoke it.

The MainWP MCP server sends the name of the AI app to your Dashboard. In Network Activity, Claude Code shows as **Claude Code**, and Claude Desktop shows as **Claude Desktop** in both chat and agent mode. Both show **AI · Claude** in the **Actor** column.

## Activity

Agent work is recorded in two places.

**Network Activity** lists each agent action with who it acted for, which AI app made it, and which key it used. See [Agent activity](/sites/network-activity#agent-activity).

The **Activity** tab on the **Agent approvals** page is for administrators. It lists agent requests, approval decisions, and settings changes, with the full command or code under **Show technical details**. Use the **Date**, **Site**, **User**, **Agent**, and **Tool** dropdowns to narrow the list.

Results use **Denied** when an administrator denies a request, **Refused** for role or access restrictions, and **Blocked** for Block rules or store restrictions. **Ran** means the action succeeded. A failed run has a failure result, such as **Run failed**; an uncertain result says **Result unknown**. A saved copy is a copy of one file for restoring that file. A safety backup covers the site before a change.

The **Agent** column shows the app and key used, in the same words as the details line in Network Activity. For an Application Password, the owner's name links to the Application Passwords section of their profile. Two other values can appear:

- **Dashboard login**: someone signed in to the Dashboard did it, such as changing the rules or a site's Agent access.
- **No agent recorded**: the row has no agent details, for example a row saved before agent details were recorded.

## Frequently asked questions

### Do I need one MCP server, or a separate one for every plugin?

One connection to your MainWP Dashboard covers all your connected sites and the plugins on them. Plugins that register WordPress Abilities show up on their own, subject to each site's Agent access setting and your permissions.

### Why use this instead of SSH and WP-CLI?

Each person uses their own rights. By default, administrators approve their own changes in their AI app, and staff changes wait for an administrator in MainWP. On sites with a backup system, MainWP checks for a recent backup and makes a safety backup if needed. Network Activity records who made the change, which AI and tool they used, and which key. You can work across 50 sites without SSH access to each one.

## Uninstalling the add-on

Uninstalling Agent Bridge deletes its own activity table and settings, including Mode, rules, and the **Activity** tab's history. The Network Activity rows in your Dashboard stay.
